## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized — reused from Phase 1, no re-init) |
| Preset | style: `new-york-v4`, baseColor: `neutral`, cssVariables: `true`, prefix: none |

| Font | Instrument Sans (Bunny Fonts), fallback `ui-sans-serif, system-ui, sans-serif` — **not** the demo's Plus Jakarta Sans; the demo is a style reference only, the real app already has a locked font from Phase 1 |

Existing installed `ui/` primitives usable as-is for this phase: `alert`, `alert-dialog`, `avatar`, `badge`, `breadcrumb`, `button`, `card`, `checkbox`, `collapsible`, `dialog`, `dropdown-menu`, `input`, `input-otp`, `label`, `navigation-menu`, `pagination`, `select`, `separator`, `sheet`, `sidebar`, `skeleton`, `sonner`, `spinner`, `switch`, `table`, `tabs`, `tooltip`.

Components NOT yet installed that this phase needs (add via `npx shadcn add {name}`, official registry, no vetting required):
- `radio-group` — Type A (print-ready) / Type B (needs consultation) selector per job order row (mutually exclusive, exactly 2 options — semantically a radio choice, not a toggle or select)
- `textarea` — customer address field (multi-line); do not reuse for the job order product/service description field (that stays a single-line `Input` per the specifics below)

Pattern precedent to follow (established in `resources/js/pages/owner/AuditTrail.vue`, the more recent implementation — not `UserManagement.vue`'s earlier raw-`<table>` pattern):
- Use shadcn `Table`/`TableHeader`/`TableBody`/`TableRow`/`TableCell`/`TableEmpty` primitives for the customer search results list, not a hand-rolled `<table>`.
- Use `router.get(..., { preserveState: true, preserveScroll: true, replace: true })` for search-as-filter interactions (customer search), matching `AuditTrail.vue`'s `visit()` function pattern.
- Use `Inertia::flash('toast', ...)` for mutation feedback (queue number generated, job orders saved) — same convention as Phase 1.

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from Phase 1, reused as-is:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge inline padding |
| sm | 8px | Compact form field gaps |
| md | 16px | Default element spacing, card padding, table cell padding |
| lg | 24px | Section padding within a portal page |
| xl | 32px | Layout gaps between major page regions |
| 2xl | 48px | Major section breaks (e.g. between "Customer" and "Job Orders" sections on the intake form) |
| 3xl | 64px | Page-level top/bottom spacing on full-page/full-bleed screens |

Exceptions:
- Interactive controls (search input, buttons, select triggers) keep the existing shadcn 40px (`h-10`)/36px (`h-9`) default heights, same exception already logged in Phase 1 — not overridden here.
- The public Queue Display page (QUEUE-06) is a full-bleed, no-chrome, TV/kiosk screen (not a portal page) — its internal grid uses the same 8-point scale, but at larger multiples appropriate for across-the-room legibility (e.g. `2xl`/`3xl` between stat cards and the queue list, rather than `md`/`lg`). No new token values are introduced — only larger members of the existing scale are used more liberally on that one screen.

## Typography

Declared values — the 4-role scale is unchanged from Phase 1, reused as-is for all portal (Frontline Staff) pages:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.4 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

- Body (14px/400/1.5): form input text, table cell values, search result rows, helper text.
- Label (14px/600/1.4): form field labels ("Name", "Contact Number", "Product / Service"), table column headers, badge text.
- Heading (20px/600/1.2): section headings within a page ("Customer", "Job Orders", "Search Results").
- Display (28px/600/1.2): page-level title ("Customer & Queue", "New Visit").

Only two weights used across the phase: 400 and 600 — same constraint as Phase 1, not relaxed here.

**Exception — public Queue Display kiosk numerals (QUEUE-06 only):** the queue number readout in each queue-entry card is **64px / 600 (semibold) / 1.1** — a one-off large-format exception for legibility from across a room on a TV/monitor. This is not a 5th role in the general scale; it applies to exactly one element on exactly one unauthenticated, no-chrome page. Status labels (Waiting/Serving/Done) on that same page use the existing Label role (14px/600) inside a badge, scaled up to 16px/600 for the same distance-legibility reason — still weight 600, no new weight introduced.

## Color

Reused as-is from Phase 1 — no new colors introduced for portal pages. The public Queue Display reuses the existing `.dark` theme tokens already defined in `resources/css/app.css` (not a new hue), applied as a deliberate kiosk treatment distinct from the light-theme portal pages.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` (light theme for portal pages; `.dark` `--background` `hsl(0 0% 3.9%)` for the Queue Display) | Page background — portal pages stay light (consistent with Phase 1); Queue Display is intentionally dark for TV/kiosk contrast |
| Secondary (30%) | `--card` / `--muted` | Card containers (customer info card, job order row cards, queue-number confirmation card), table zebra/header background |
| Accent (10%) | `--primary` | Reserved for: primary submit buttons ("Search Customers", "Register New Customer", "Add to Queue"), the queue-number confirmation card's number value, active nav indicator, focus rings — same reservation list as Phase 1, extended with the queue-number display |
| Destructive | `--destructive` | Reserved for: duplicate-contact-number validation error, "Register New Customer" disabled/locked state messaging is NOT destructive (informational, not an error) |

Additional semantic color for this phase (extends, does not replace, Phase 1's contract):

| Role | Value | Usage |
|------|-------|-------|
| Success (queue "Done" status only) | Tailwind `green-600` (light) / `green-400` (dark) | Reserved exclusively for the "Done" queue-status badge, both on the Frontline Staff queue list and the public Queue Display. This follows the existing in-codebase precedent (`text-green-600` already used in `Login.vue`/`ForgotPassword.vue` for success messaging) rather than inventing a new CSS custom property. |

Queue status badge color mapping (applies to both the Frontline Staff internal queue list and the public Queue Display):
- **Waiting** → `Badge variant="outline"` (lowest emphasis, not yet actionable)
- **Serving** → `Badge variant="default"` (uses `--primary`, highest emphasis — currently being handled)
- **Done** → `Badge` with `text-green-600 dark:text-green-400` override (success precedent above)

Accent reserved for: primary form submit buttons, active nav indicator, focus states, hyperlinks, and the queue-number confirmation display value only. Never used for decorative fills or as a general highlight on non-interactive elements — same rule as Phase 1.

## Phase-Specific UI Notes

**Two distinct surfaces in this phase — do not conflate their visual treatment:**
1. **Frontline Staff portal pages** (customer search/register, queue + job order intake) — authenticated, inside the existing `AppSidebarLayout` shell, `frontline-staff` role nav (currently empty per `resources/js/config/nav/` convention — this phase populates `resources/js/config/nav/frontline-staff.ts` following the exact pattern of `resources/js/config/nav/owner.ts`). Light theme, standard portal typography/spacing/color contract above.
2. **Public Queue Display** (QUEUE-06) — unauthenticated, full-bleed, no sidebar/header chrome at all (not `AppSidebarLayout`, not `AuthLayout`). Follow the `Welcome.vue` precedent for opting out of layout: place the page at `resources/js/pages/public/QueueDisplay.vue` and add a new case to the layout switch in `resources/js/app.ts` (`case name.startsWith('public/'): return null;`) so it renders with zero chrome. Dark theme (reuse `.dark` tokens, do not invent new hex values), large-format typography per the Typography exception above.

**Customer search + register flow (D-03, D-04):**
- Single search bar (`Input` + "Search Customers" `Button`) searching name OR contact number with partial/LIKE matching (not exact).
- Results render in a `Table` (per `AuditTrail.vue` precedent): Name, Contact Number, Email columns, each row clickable/selectable to proceed to queue intake for that customer.
- "Register New Customer" button is disabled/hidden until a search has been run and returned zero results — this is a state-gated affordance, not a permanently-visible button that validates on submit. Show it inline below the empty `TableEmpty` state, not as a separately-navigated page, so the flow stays "search → (zero results) → register → intake" in one continuous screen.
- Registration form fields (D-01): Name (`Input`), Contact Number (`Input`, `type="tel"`), Email (`Input`, `type="email"`), Address (`Textarea`, 2–3 rows). Contact Number's uniqueness violation (D-02) surfaces via the standard `InputError` component under that field, not a toast — it's a field-level validation error.

**Queue + job order intake form (D-05 through D-15), single combined form (D-14):**
- Layout: two-region form on one page — a compact "Queue Visit" header/summary area (customer name + a placeholder for the queue number, populated only after save) above a repeatable "Job Orders" section.
- Each job order row is a `Card` containing: Product/Service description (`Input`, single line, placeholder e.g. "Tarpaulin, 3×5ft" per D-12), Type A/Type B selector (`RadioGroup`, two `RadioGroupItem`s labeled "Type A — Print-ready file" / "Type B — Needs consultation"), and conditionally a file attach control (`Input type="file"` styled as a `Button`, per "Attach File" copy above) shown only when Type A is selected. No DPI/format/size validation UI in this phase (D-11) — no error states for file rejection belong here.
- "+ Add Another Job Order" appends a new row card; each row beyond the first shows a "Remove" icon button. No hard maximum (D-15).
- On submit ("Add to Queue"), the queue number is generated server-side and the confirmation state replaces (or is inserted above) the form: a prominent card showing the queue number in large type (mirroring the demo's `queue-id-box` layout pattern — label + large number + sub-label, translated into shadcn `Card` + the Display/accent-colored number, not the demo's blue palette) alongside a summary list of the job orders just created (product description + Type A/B `Badge` for each).

**Frontline Staff internal queue list (supports D-05, D-08):**
- A `Table` of today's queue entries: Queue Number, Customer Name, Status (`Badge`, color-mapped per the Color section above), and action buttons ("Call Next" / "Mark Done") shown contextually based on current status (Waiting shows "Call Next"; Serving shows "Mark Done"; Done shows no action). This is the internal, authenticated counterpart to the public display — it may show customer names (PII is fine here since it's role-gated), unlike the public display.

**Public Queue Display (D-09, D-10):**
- No customer names or any PII — number and status only (D-09), enforced by what the controller sends to the page, not just by hiding it client-side.
- Client-side polling: use `router.reload({ only: ['queueEntries'], showProgress: false })` on a `setInterval` (suggest 5s, matching the demo's stated cadence) rather than a raw `fetch`, to stay inside the existing Inertia-only data-fetching convention this app uses everywhere else (no separate JSON API layer exists per `PROJECT.md`).
- Visual structure takes cues from `demo/queue-display.html`'s layout rhythm (header with live clock + "Live" pulsing indicator, stat summary row, main list) but rebuilt entirely in the app's own dark theme tokens and Instrument Sans — not the demo's blue palette or Plus Jakarta Sans font.
- Layout: group or sort entries by status (Waiting first, then Serving, then Done — or three columns) so the busiest information (who's being served next) is scannable at a glance without reading every row.
