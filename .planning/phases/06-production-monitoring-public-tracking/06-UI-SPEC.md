### Urgency palette (PROD-01) — the one genuinely new colour axis

PROD-01 locks two colours by name: **Green = Normal, Amber = Rush**. The neutral theme has no such tokens, so this phase declares them as Tailwind utility pairs in the exact shape of the existing `text-green-600 dark:text-green-400` success override already used for "Done" / "Ready for Production" / "Design Approved" / "Paid". These are **semantic data encodings on one axis only** — not decoration, not a theme change.

| Urgency | Rule (D-05 / D-07) | Badge | Row treatment |
|---|---|---|---|
| **Normal** | `due_at` is after today | `<Badge variant="outline" class="text-green-600 dark:text-green-400 border-green-600/40">Normal</Badge>` | none |
| **Rush** | `due_at` is today or in the past | `<Badge variant="outline" class="text-amber-600 dark:text-amber-400 border-amber-600/40">Rush</Badge>` | `class="bg-amber-50 dark:bg-amber-950/20"` on the `TableRow` — a secondary scan cue only (the demo's MINOR-3 row tint) |

**Accessibility rule (binding):** urgency is **never encoded by colour alone**. The badge always carries the literal word "Rush" or "Normal", and Rush additionally carries a lucide `Zap` icon at `xs` (4px) gap. A colour-blind or greyscale-printing user reads the word. The row tint is redundant reinforcement, never the sole signal.

### Stage colour: explicitly NOT coloured

CONTEXT.md `<specifics>` flagged the collision directly: the demo gives For Production green, Printing amber, Quality Check violet, Ready for Pickup blue — which would put green and amber on the same card as the urgency axis and destroy PROD-01's two-colour meaning.

**Resolution (this is the UI pass's call, as CONTEXT.md delegated): urgency owns colour; stage does not.** Stage badges are monochrome, distinguished by label text only — the same rule Phase 4 already set for `in_consultation` vs `in_design` ("distinguished by label text only, not color"). The demo's violet/blue values are decoration and are not reused.

| `JobOrderStatus` value | Display label | Badge treatment | Meaning |
|---|---|---|---|
| `for_production` | "For Production" | `variant="outline"` | On the board, not started — mirrors "Waiting" / "Awaiting Assignment" |
| `printing` | "Printing" | `variant="secondary"` | In progress — same tier as `in_design` |
| `quality_check` | "Quality Check" | `variant="secondary"` | In progress — distinguished by label text only |
| `ready_for_pickup` | "Ready for Pickup" | `class="text-green-600 dark:text-green-400"` (no `variant` prop, matching the existing "Done" / "Paid" success precedent exactly) | Production complete; awaiting Frontline release |

Phase 3/4/5's existing badge mappings (`intake`, `ready_for_production`, `assigned`, `in_consultation`, `in_design`, `pending_review`, `design_approved`, `validation_failed`, and every `payment_status` badge) stay **exactly** as their specs defined them. Lifecycle status and payment status remain two separate badges and must never be merged.

### Public tracking page colour

The public page inherits `QueueDisplay.vue` / `DesignReview.vue`'s forced-dark public shell (`class="dark bg-background text-foreground"`). It shows **no urgency colour at all** — urgency is an internal SLA signal, not customer information. Only two colour treatments appear: the success green above for "Ready for Pickup" and "Completed", and default foreground for everything else.

**Accent reserved for:** the additions listed in the table above only. Never used for decorative fills — same rule as every prior phase.

## Phase-Specific UI Notes

**Three new surfaces and three bounded extensions. Do not build anything beyond these.**

### 1. Production Board (`resources/js/pages/production-staff/Dashboard.vue`, replaces the current placeholder)

**Layout decision (CONTEXT.md delegated this to the UI pass): a single urgency-sorted table with stage filter tabs — not a kanban.** Reasons, in order of weight:

1. **PROD-02 safety.** A kanban's affordance is drag-anywhere; D-10 forbids skipping stages. A table row whose only forward control is one button *named after the single legal next stage* makes skipping unrepresentable in the UI, rather than merely rejected by the server.
2. **No new dependency.** Kanban drag-and-drop needs a DnD library; PROJECT.md gates every dependency change on approval, and this phase otherwise adds none.
3. **Urgency is the primary sort axis** (PROD-01), and urgency cuts *across* stages. A kanban forces stage to be the primary organiser and buries the rush order in column three.
4. **House consistency.** Every internal list surface in this app is a shadcn `Table` (`QueueList.vue`, `AuditTrail.vue`, `DesignOverrides.vue`, `CreditRequests.vue`, cashier `Dashboard.vue`). The demo's own production queue is a table too.

Page structure, top to bottom, `lg` (24px) gaps:

- **H1** "Production Board" (Display).
- **Rush `Alert`** — rendered only when the Rush count > 0. Uses the amber urgency utilities (`text-amber-600 dark:text-amber-400`), a lucide `Zap` icon, and the copy above. **Never `variant="destructive"`** — a rush order is a priority signal, not an error (same rule Phase 4 set for the "Exceeded break time" indicator).
- **Four stat `Card`s** in a responsive row (`grid grid-cols-2 gap-4 md:grid-cols-4`): count at Display size, caption at Label size, matching the four stage names.
- **Stage filter `Tabs`** — `TabsList` with `TabsTrigger`s "All" / "Rush" / the four stage names. **Client-side filtering over the already-polled array** (a day's production is tens of rows, not thousands): no query param, no server round-trip, and the selection therefore survives every 5-second poll without any extra work. Active tab uses `--primary`.
- **Board `Table`** — columns per the Copywriting Contract. Default sort: Rush first, then by `due_at` ascending, then by job order number. Rush rows carry the tint from the Color section.
  - **Actions cell** — up to two `size="sm"` buttons, `sm` (8px) gap:
    - Forward: one `--primary` button labelled with the destination stage. Absent at `ready_for_pickup`, replaced by the muted "Awaiting release" text.
    - Backward: `variant="outline"` "Send Back to {previous stage}", opening the reason `Dialog`. Absent at `for_production` (nothing precedes it).
    - **No stage `<Select>`.** The demo's `pd-status-select` lets a user jump from For Production straight to Ready for Pickup; that directly violates PROD-02 and is explicitly not reused.
  - Empty states per the Copywriting Contract, rendered via `TableEmpty`.
- **Polling** — `usePoll(5000, { only: [...] })` per D-14, mirroring `QueueDisplay.vue`'s exact pattern.

**Stale-advance handling (real risk: two production staff, one board, a 5-second poll).** The server is authoritative on the sequence rule. When it rejects a move because the row already changed, surface the "already moved on" `Alert` from the Copywriting Contract inline above the table — never a silent no-op, and never a client-side-only guard.

**Deliberately absent from the board — payment.** The demo shows `paid` / `paymentState` / `balance` on every production card. This spec omits payment entirely: Phase 5 D-15 establishes that payment never gates production, so a payment badge here can only mislead; the release gate already lives on the Frontline surface where it belongs; and it keeps money data out of a role that has no business need for it. CONTEXT.md permits an informational payment hint — this spec declines it.

**Also out of scope for this surface:** no job-order detail page, no design-file preview, no activity-log panel. The demo has all three; PROD-01/02/03 ask for none of them, and the design-file surface is Phase 4's.

**Nav:** create `resources/js/config/nav/production-staff.ts` (does not exist yet — the same state `accounting-staff.ts` was in before Phase 5) with a single item: title "Production Board", icon lucide `Factory`, href `dashboard()`. This is a deliberate departure from the other portals' generic "Dashboard" / `LayoutGrid` first item: PROD-01 names this surface a board, the page H1 says "Production Board", and a nav label that disagrees with the page title is worse than an inconsistent icon. Route name `production-staff.dashboard` is **unchanged** — only `Route::inertia` is swapped for a controller.

### 2. Frontline Ready-for-Pickup list (`resources/js/pages/frontline-staff/Dashboard.vue`, replaces the current placeholder)

**Placement decision (CONTEXT.md left the Release button's home to planning; this spec settles the alert's home):** the alert lives on the Frontline **Dashboard**, the post-login landing page.

- It matches the precedent Phase 5 set twice (cashier and accounting placeholder dashboards were replaced by the first real surface their phase produced).
- It makes PROD-03's "receives an alert" literal: the list is in front of Frontline Staff on arrival, with no navigation required.
- It needs no change to the shared `NavItem` type or `NavMain.vue`. A live count badge on the sidebar was considered and **rejected**: `resources/js/types/navigation.ts` has no badge field and `defineOptions({ layout: { navItems } })` is a static compile-time array, so a dynamic count would mean re-plumbing layout props across all seven portals — far outside this phase's blast radius.

Structure: H1 "Frontline Dashboard" (Display), then a "Ready for Pickup" section (Heading + sub-copy), then a `Table` with the columns from the Copywriting Contract, `TableEmpty` for the empty state, and `usePoll(5000, { only: [...] })` per D-14. The "Payment" column reuses the **existing** Phase 5 `payment_status` badge mapping verbatim — it is present here (unlike on the production board) precisely because this is the surface where the release gate applies.

**"Release to Customer"** calls the existing `JobOrderReleaseController::store` action (`frontline-staff.job-orders.release`). **The `QueueList.vue` button from 05-UI-SPEC §6 is retained, not superseded** — this Dashboard button is a second entry point to the same gated action, not a replacement. Both are correct because both call the identical server action; the release gate lives in the controller, so there is no duplicated eligibility logic to keep in sync. It is never re-implemented and its client-side eligibility predicate never becomes the gate — the blocked-message `Alert` copy is quoted verbatim from 05-UI-SPEC. An order can legitimately reach Ready for Pickup unpaid (Phase 5 D-15), so the blocked path is a normal, expected outcome here, not an edge case.

### 3. Ready-for-pickup banner on the Queue page (`resources/js/pages/frontline-staff/QueueList.vue`, extension only)

For staff already working inside the queue page, add a polled `Alert` at the top (above the H1's table, below the H1) using the banner copy above, with a lucide `PackageCheck` icon and a link to the Dashboard. Rendered only when the count > 0. `usePoll(5000, ...)` is added to this page with the ready-for-pickup count included in the partial reload.

**Nothing else on `QueueList.vue` changes** except the identifier swap in §6.

### 4. Public tracking page (`resources/js/pages/public/Tracking.vue`, new)

Lives under the `public/` page namespace, so `resources/js/app.ts`'s existing `name.startsWith('public/')` case gives it **zero chrome** — no sidebar, no header, no auth nav. Follows `QueueDisplay.vue` and `DesignReview.vue`'s forced-dark public shell: `class="dark bg-background text-foreground"`, a centred single `Card` at `max-w-md mx-auto`.

**One page, two states:**

- **Lookup state** — heading, sub-copy, `Label` + `Input` ("Job Order Number", placeholder `JO-2026-0001`, `autocapitalize="characters"`), and a full-width `--primary` "Check Status" submit showing a `Spinner` while in flight. Field-level `InputError` for a malformed number. **This state does not poll.**
- **Result state** — the echoed "Job Order {number}" at Heading size in `text-muted-foreground`, the mapped stage label at Display size beneath it, the "This page updates automatically." note at Body size, and a "Check another order" link back to the lookup state. **Polls at 5000ms** (D-14) with a partial reload of the status prop only. Polling starts only in this state — the bare lookup form must never poll.
- **Not-found** — the same card renders the "We couldn't find that order" `Alert` plus the lookup form again, so the customer can retype without navigating.

**Route shape (recommended, not mandated — the planner owns it):** `GET /track` for the form and `GET /track/{number}` for the deep-linked result, both public, both `throttle:60,1` alongside the three existing public-route precedents. A short path keeps the printed fallback URL speakable.

### 5. Public status mapping — TRACK-02's PII boundary, expressed as a UI contract

**Binding contract: the browser payload for the public tracking page contains exactly two fields — the job order number the customer just typed, and a pre-mapped public status *string*.** The raw `JobOrderStatus` enum value never reaches the client, and no other column ever joins the payload. This is the same explicit-allowlist discipline `QueueDisplayController` documents, applied one level stricter: the mapping happens server-side so that even the internal status vocabulary stays inside the server.

| Internal state | Public label shown |
|---|---|
| `intake`, `validation_failed`, `ready_for_production`, `assigned`, `in_consultation`, `in_design`, `pending_review`, `design_approved` | "In Progress" |
| `for_production` | "For Production" |

Collapsing every pre-production state into "In Progress" is deliberate: it answers the customer's actual question, and it prevents the public page leaking that a file failed validation or that a design is sitting in review — internal states the customer has no context for and TRACK-02's spirit excludes.

**Explicitly not on this page** (D-02, the strictest reading of TRACK-02): no timeline or stepper of passed stages, no product description (customer-authored free text — CONTEXT.md rejected it by name as a silent weakening of the no-PII guarantee), no customer name, no price, no payment status, no balance, no due date, no urgency colour, no design file or thumbnail, no assigned staff name, no queue number.

### 7. Receipt QR (D-03, extension only)

Add a new thin wrapper `resources/js/components/TrackingQrCode.vue` (props: `trackingUrl: string`) alongside the existing `PaymentQrCode.vue`. **Do not repurpose `PaymentQrCode.vue`** — it is the on-screen PayMongo redirect QR at 240px canvas and stays untouched.

- Renders `<QrcodeVue :value="trackingUrl" :size="160" render-as="svg" level="M" />`. **SVG, not canvas**: the receipt's whole purpose is `window.print()`, and an SVG QR prints crisply at any printer DPI while a canvas QR is a fixed-resolution raster that browsers can drop from print output entirely.
- Placed in its own bordered block at the bottom of the Receipt `Card` (`border-t pt-4`, matching the card's existing section dividers), centred, with the caption at Body size in `text-muted-foreground` beneath it, then the typed fallback line beneath that.
- **Must not carry `print:hidden`** — it is the single most important thing on the printed receipt for this phase. The existing `print:hidden` on the "Print Receipt" button is unchanged.
- The QR encodes the deep link to *that* order's status, so scanning lands on the result state directly with nothing to type (D-03). The typed fallback exists for a torn or smudged receipt.
