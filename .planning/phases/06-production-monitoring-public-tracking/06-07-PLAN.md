<objective>
Close the regression the plan-checker found in 06-04: wiring `EnterProduction` immediately after every real `DesignApproved` write means a Type B job order is never again observably at `DesignApproved` once it has been approved through either real approve() path — it always advances to `ForProduction` (or beyond) in the same transaction. Four downstream consumers of `DesignApproved`/`ReadyForProduction` were missed by 06-04's own audit: the Cashier's cancellation-fee trigger (POS-07), the Artist's Performance Report completion metric (JOB-10), the Artist's own queue-exclusion list and status display, and the Cashier Dashboard's Status badge. This plan re-audits every remaining consumer exhaustively (including two additional display-only staleness gaps found during that re-audit, in Frontline's Queue and New Visit pages) and fixes all of them together, since they share one root cause.

Purpose: Without this plan, a job order that has done the most design work possible (fully approved AND already in production) would silently be treated by the Cashier as if design had never started (no fee on cancellation), would permanently zero out every artist's performance metrics from the moment 06-04 ships, and would either pile up forever in the Artist's queue or render with a blank/stale status badge on four different staff-facing pages.
Output: `CancellationController`, `PerformanceReportController`, and `JobOrderQueueController` all extended to recognize the four new production statuses as "past DesignApproved, not before it"; `cashier/Dashboard.vue`, `artist/Dashboard.vue`, `frontline-staff/QueueList.vue`, and `frontline-staff/NewVisit.vue` all extended to render a real badge/label for those statuses; every fix proven with a test that drives a job order through the real `approve()` -> `EnterProduction` path, never a factory-injected `status` shortcut.
</objective>
