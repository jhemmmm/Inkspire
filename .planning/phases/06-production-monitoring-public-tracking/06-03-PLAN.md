<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `GET /track` | Fully unauthenticated, public internet-facing, keyed on a guessable sequential identifier |
| Receipt QR payload | Client-constructed from a server-issued absolute URL; the QR itself carries no secret, just the same public tracking link a human could type |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-03-01 | Information Disclosure | `TrackingController::show()` payload | mitigate | Explicit column allowlist (`['number', 'status', 'released_at']` on the query, `['found', 'number', 'stage']` in the response) — `status` is read but never serialized raw, only through `publicStage()`'s match expression. Covered by an automated test asserting `total_amount`/`payment_status`/`file_path`/`description` never appear in the response body. |
| T-06-03-02 | Information Disclosure / Enumeration | Sequential `JO-{year}-seq}` identifier, unauthenticated lookup | accept | D-01 explicitly accepts this — an attacker can enumerate valid numbers and learn only a job order's coarse public stage (e.g. "Printing"), never PII, pricing, or payment. Mitigated by T-06-03-03's rate limit; not re-opened here. |
| T-06-03-03 | Denial of Service / Enumeration aid | Unthrottled brute-force lookups | mitigate | `throttle:60,1` on the route, matching the existing public-route convention (`queue-display`, `design-review`, `webhooks/paymongo`). |
| T-06-03-04 | Tampering | Receipt QR content | accept | The QR encodes a `GET` URL to a read-only, allowlisted endpoint — scanning it can only ever reveal the same coarse status a human typing the number would see. No mutation is reachable via the QR. |

</threat_model>
