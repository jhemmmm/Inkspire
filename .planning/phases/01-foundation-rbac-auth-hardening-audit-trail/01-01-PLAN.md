<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Application code -> audit_trail table | Every write must be an append (`create()`); no code path may issue `update()`/`delete()` against `AuditLog` |
| Eloquent mutation -> AuditObserver | Any model author who forgets `#[ObservedBy(AuditObserver::class)]` silently produces no audit trail for that model — a config/wiring risk, not a runtime attacker-controlled one |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-01-05 | Repudiation | `app/Models/AuditLog.php`, `app/Support/AuditLogger.php` | mitigate | No `update()`/`delete()` code path exists anywhere in `app/` for `AuditLog` (D-04); every row captures `user_id` + `ip_address` so an action cannot be plausibly denied; enforced by `tests/Unit/Arch/AuditLogArchTest.php` grepping `app/` for the two forbidden static-call forms on every CI run |
| T-01-06 | Denial of Service | `users.locked_until`/`failed_login_attempts` columns (schema only in this plan; enforcement lands in Plan 01-07) | accept | Accepted risk at this shop's scale — an attacker who knows a valid email can lock out that account by repeatedly failing login; mitigated in practice by another Admin/Owner's ability to manually reactivate via User Management (Plan 01-11); no additional mitigation planned for Phase 1 |
</threat_model>
