<objective>
Build the data substrate for CONFIG-01 (key-value `system_configurations` table, model with cached typed accessors, and a seeder covering every business rule the requirement names) so that Plan 01-07 (account lockout) and Plan 01-08 (idle timeout) can read real configured thresholds instead of hardcoded literals, and Plan 01-12 can later build the CRUD UI on top of this without any schema change.

Purpose: CONFIG-01 explicitly needs to support new keys across Phases 3/4/8 without migrations — a key-value shape (not fixed columns) is the correct fit (RESEARCH.md Pattern 6, Alternatives Considered).
Output: `system_configurations` table + `SystemConfiguration` model (audited via `#[ObservedBy(AuditObserver::class)]`, same as `User` in Plan 01-01) + `SystemConfigurationSeeder` with all 12 keys grouped to match the UI-SPEC's 3 tabs (Security, Business Rules, File Handling).

Scope note (CONFIG-01 "per-product SLA"): this plan deliberately delivers `default_sla_days` as a single global value, not a per-product override, because no `products` table exists until Phase 3/5 — there is nothing to key a per-product override against yet. This is a sequencing decision, not a scope reduction: the per-product override will extend or replace this key once the Phase 3/5 pricing tables land.
</objective>

  <action>
    Run `php artisan make:migration create_system_configurations_table --create=system_configurations --no-interaction`. Columns: `$table->id();`, `$table->string('key')->unique();`, `$table->string('group');` (values: `security`, `business_rules`, `file_handling`), `$table->json('value');`, `$table->string('type');` (values: `integer`, `decimal`, `boolean`, `string`, `array`), `$table->string('label');`, `$table->text('description')->nullable();`, `$table->timestamps();`.

    Run `php artisan make:model SystemConfiguration --no-interaction`. Add `use Illuminate\Database\Eloquent\Attributes\ObservedBy;` and `#[Fillable(['key', 'group', 'value', 'type', 'label', 'description'])]` and `#[ObservedBy(\App\Observers\AuditObserver::class)]` as class attributes (same pattern as `User` in Plan 01-01 — this is what makes every create/update of a config row produce an `audit_trail` row automatically, with zero involvement from the future Plan 01-12 controller). Add a `casts(): array` method returning `['value' => 'array']`. Add four static accessor methods, each `Cache::rememberForever("config.{$key}", ...)`-backed:
    - `getInt(string $key, int $default): int` — `(int) (static::where('key', $key)->value('value') ?? $default)` (note: `value` column decodes JSON automatically via the array cast when loaded through a model instance, but `::where(...)->value('value')` is a raw column read that bypasses casting — read the row via `static::query()->where('key', $key)->first()?->value ?? $default` instead, so the JSON cast applies, then cast to `(int)`).
    - `getBool(string $key, bool $default): bool` — same lookup pattern, cast to `(bool)`.
    - `getArray(string $key, array $default = []): array` — same lookup pattern, return the decoded array directly (already an array via the `value` cast) or `$default` if the key is missing.
    - `getString(string $key, string $default): string` — same lookup pattern, cast to `(string)`.
    Also add `public static function invalidate(string $key): void` calling `Cache::forget("config.{$key}")`, to be called by the future config-update controller (Plan 01-12) immediately after saving a changed row (RESEARCH.md Pitfall 5 — `rememberForever` has no TTL and must be invalidated explicitly on write, not left to expire).

  </action>
