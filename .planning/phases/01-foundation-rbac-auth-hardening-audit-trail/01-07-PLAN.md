<objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Failed-login counter -> account lockout | Counter increments are keyed off a server-resolved `User` row, never client input directly |
| Locked/deactivated rejection -> pipeline ordering | Must run strictly before `AttemptToAuthenticate` so a correct password never bypasses the lockout/deactivation check |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-01-02 | Spoofing | `app/Actions/Fortify/EnsureAccountIsNotLocked.php`, `app/Listeners/Auth/RecordFailedLoginAttempt.php` | mitigate | Account-level lockout (this plan) is defense-in-depth alongside the existing IP+email `RateLimiter` (unchanged) — two independent triggers per RESEARCH.md's Known Threat Patterns table |
| T-01-06 | Denial of Service | `users.locked_until` | accept | An attacker who knows a valid email can lock that account by repeatedly failing login; accepted for this shop's scale, mitigated by another Admin/Owner's ability to inspect and manually intervene via User Management (the account self-unlocks after `account_lockout_minutes` regardless) |
| T-01-05 | Repudiation | `RecordFailedLoginAttempt`, `RecordLockoutEvent` | mitigate | Every failed attempt and every lockout (both account-level and IP-throttle-level) is captured in `audit_trail`, giving Owner/Admin full visibility into brute-force attempts against any account |
</threat_model>
