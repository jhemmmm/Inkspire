<objective>
Give the Cashier portal its first real capability: open a production-ready or design-approved job order, price it against the catalog (POS-01), and record a Cash or Bank Transfer payment — full or as a down payment with a tracked remaining balance (POS-02, POS-05). This plan also lays the shared data foundation (payment_status column, pricing_database, transactions) that every other Phase 5 plan builds on, per D-01 through D-05.

Purpose: This is the first vertical slice of the phase's money flow — nothing else in Phase 5 (receipts, GCash/Maya, reconciliation, cancellation, on-credit, release-gating) can be built without these three tables and this page existing first.
Output: `pricing_database`/`transactions` tables, `job_orders` payment columns, `ComputeJobOrderPrice` action, `PaymentController`, and a working Cashier Dashboard → Job Order Payment page for Cash/Bank Transfer.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (Cashier) → PaymentController@store | Cashier-submitted pricing/payment form fields cross into server-authoritative money computation |
| Cashier session → job_orders/transactions writes | Every write here is a financial mutation requiring full audit coverage |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-05-03 | Tampering | `PaymentController@store` | mitigate | Server always recomputes `total_amount` via `ComputeJobOrderPrice` from `line_amount`/`rush_fee_applied`/`discount_value` — a client-submitted `total_amount` field is never read or trusted, per RESEARCH.md's explicit "money math must be server-authoritative" architecture-map row |
| T-05-04 | Tampering | `PricingValidationRules::pricingRules()` discount closure | mitigate | Discount value is validated server-side against `SystemConfiguration::getFloat('discount_cap_percentage'/'discount_cap_flat_amount')`, never a client-supplied cap |
| T-05-05 | Repudiation | `Transaction`, `JobOrder` (payment columns) | mitigate | Both carry `#[ObservedBy(AuditObserver::class)]`; every payment write is captured in `audit_trail` with `recorded_by` attribution |
| T-05-06 | Elevation of Privilege | `cashier.job-orders.payment.*` routes | mitigate | Routes sit inside the existing `role:cashier` middleware group (`EnsureUserHasRole`, `abort_if` 403 pattern) — no other role can reach this controller |
| T-05-07 | Repudiation | Double-submission of the same payment (Cashier double-clicks "Record Payment") | accept | Full payment idempotency for Cash/Bank Transfer is lower-risk than GCash/Maya (no external gateway race) — `abort_if(payment_status === Paid)` on the second call prevents double-crediting a *completed* job order; a rapid double-click before the first request resolves could theoretically create two transactions summing over `total_amount`, but Cash/Bank Transfer are synchronous single-request operations with no network-retry window like PayMongo's, so this is accepted risk for this plan, matching ASVS L1 scope (Plan 05-03's `ConfirmPaymentIntent` gets the full lock-guarded treatment specifically because that path DOES have a real double-delivery risk) |
