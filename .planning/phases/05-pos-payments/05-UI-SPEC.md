# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Source: `.planning/phases/05-pos-payments/05-CONTEXT.md` (locked decisions D-01 through D-16, Claude's Discretion list), `.planning/phases/05-pos-payments/05-RESEARCH.md` (recommended schema/enums, PayMongo architecture, `qrcode.vue` dependency), `.planning/phases/01-.../01-UI-SPEC.md` through `04-UI-SPEC.md` (authoritative baseline design system — reused, not re-litigated), `components.json` + `resources/css/app.css` (live token state), `resources/js/pages/frontline-staff/QueueList.vue` + `NewVisit.vue`, `resources/js/pages/owner/UserManagement.vue` + `AuditTrail.vue` + `DesignOverrides.vue`, `resources/js/pages/cashier/Dashboard.vue` + `resources/js/pages/accounting-staff/Dashboard.vue` (current empty placeholders this phase replaces), `app/Enums/JobOrderStatus.php`, `app/Enums/UserRole.php`, `routes/portals.php` (live reference implementations read directly, not assumed). `demo/main.js` (POS section, lines ~2900-3150) referenced **only** for the payment-method ordering (Cash → GCash → Maya → Bank Transfer) and the receipt field layout (JO number, total, tendered, balance) that CONTEXT.md's `<specifics>` section confirms it's authoritative for — the demo's per-method brand colors (blue/green/purple) and its "cs-bank-pending-toggle" manual-confirmation pattern are explicitly **not** reused (this project's Bank Transfer records complete immediately, and every color/spacing/type value below stays inside this app's existing neutral shadcn theme, matching the precedent Phase 4 already set for ignoring the demo's palette).

This phase replaces the Cashier and Accounting Staff portals' placeholder dashboards with real POS/reconciliation surfaces, adds one new Owner-facing surface (Credit Requests), and extends the Frontline Staff portal with one new action (Release to Customer). No new shadcn primitives are required — every component this phase needs is already installed. The one new dependency is `qrcode.vue` (plain npm package, not a shadcn registry block — see Registry Safety below).

Existing installed `ui/` primitives usable as-is for this phase — **no new `npx shadcn add` calls required**:

- `table` — Cashier Dashboard, Accounting Staff Dashboard, Owner Credit Requests list

- `card` — Pricing section, Payment section, GCash/Maya QR sub-view, Receipt layout, stat-style summaries
- `dialog` — Cancellation dialog's fee breakdown precedes an `alert-dialog` confirm (see below); no plain-`Dialog` surfaces needed beyond what already exists

- `radio-group` — Payment method selection (Cash/Bank Transfer/GCash/Maya/On Credit), payment type (Full/Down), catalog-adjustment discount type — mirrors `NewVisit.vue`'s exact Type A/B `RadioGroup` + `RadioGroupItem` + `Label` list pattern (plain list rows, **not** colored/bordered "cards" — see Color section for why the demo's per-method card colors are explicitly not reused)
- `select` — Catalog product/service pick (POS-01) from `pricing_database`
- `switch` — Rush fee toggle (D-03)
- `input` (`type="number"`, `type="text"`) — adjusted line amount, discount value, amount tendered, bank reference number
- `dropdown-menu` — per-row "Actions" menu on Cashier Dashboard (Process Payment / Check Payment Status / View Receipt / Release to Customer / Cancel Job Order — contextual by state, see Phase-Specific UI Notes)
- `alert` (+ existing `AlertError.vue` wrapper) — payment/pricing validation failures, reconciliation "still pending" results
- `spinner` — reconciliation "Check Payment Status" in-flight state, GCash/Maya intent-creation in-flight state
- `button`, `label` — standard form/action controls throughout

No registry additions this phase.

**New non-shadcn dependency:** `qrcode.vue` (npm, framework-agnostic Vue 3 component — see `05-RESEARCH.md` Standard Stack, `slopcheck`-approved). Rendered directly inside the GCash/Maya QR sub-view — no wrapper component needed beyond a thin `PaymentQrCode.vue` that takes the PayMongo `redirect.url` as a prop. This is **not** a shadcn registry block, so the `npx shadcn view --registry` vetting gate does not apply — see Registry Safety below.

**Destructive confirmation:** three high-stakes, money-moving actions get `AlertDialog` treatment (matching the existing "Deactivate Account" / "Unlock Design" precedent — reserve `alert-dialog` for irreversible/high-stakes actions, not routine status changes):

1. **"Cancel Job Order"** — collects a fee, cannot be undone. Confirm button uses `variant="destructive"`.
2. **"Approve Credit"** (Owner) — posts real money to Accounts Receivable; high-stakes but a positive outcome. Confirm button uses `--primary` styling (not destructive), matching Phase 4's "Client Approved" precedent (irreversible-but-positive actions don't get red buttons).
3. **"Reject Credit"** (Owner) — final state with no auto-fallback (D-07). Confirm button uses `variant="destructive"`, since it blocks the job order's payment path and requires manual follow-up.

**On-Credit request** (Cashier-side, D-06) also gets a lightweight `AlertDialog` — not because it's destructive, but because it changes the job order's payment path to something only an Owner can move forward, and the Cashier should see that framing before submitting. Confirm button uses `--primary` styling.

Every other action this phase introduces — "Record Payment", "Record Down Payment", "Generate QR Code", "Check Payment Status", "Release to Customer" (when allowed) — is a plain `Button`/`Form` submit with **no** confirmation dialog, matching the existing "Call Next"/"Mark Done"/"Save Consultation Notes" precedent.

## Phase-Specific UI Notes

**New/replaced surfaces this phase builds — six in total. Do not build anything beyond these:**

### 1. Cashier Dashboard (`resources/js/pages/cashier/Dashboard.vue`, replaces the current placeholder)

One `Table` (per `AuditTrail.vue`/`QueueList.vue` precedent — not a hand-rolled `<table>`) listing job orders eligible for POS action: any job order with `status` in `ready_for_production`/`design_approved` (i.e., production-ready per Phase 3/4) whose `payment_status` is not yet a terminal state. Columns: Job Order, Customer, Description, Job Order Status (badge, unchanged from Phase 3/4), Payment Status (badge, per the mapping above), Actions.

Actions column uses a `DropdownMenu` (lucide `MoreHorizontal` trigger, `sr-only` "Actions" label) rather than several inline buttons, since up to five contextual actions can apply to one row:

- `payment_status` is `unpaid` / `partially_paid` / `credit_rejected` → "Process Payment" (navigates to §2)
- `payment_status` is `pending_confirmation` → "Check Payment Status" (inline reconciliation, per D-12 — same action as Accounting's, see §5)
- `payment_status` is `paid` / `on_credit` → "View Receipt" (navigates to §3)
- Any non-cancelled, non-terminal-paid status → "Cancel Job Order" (opens the dialog per Copywriting Contract, D-04/D-05)
- `payment_status` is `paid` or `on_credit` (active) and not yet released → "Release to Customer" — **see §6 below: this action's authoritative home is the Frontline Staff portal**; if planning finds it more natural to also surface here for Cashier convenience, it must call the same server-side gated action, never a client-only check.

Empty state per Copywriting Contract, rendered via `TableEmpty`.

### 2. Job Order Payment page (`resources/js/pages/cashier/JobOrderPayment.vue`, new — one page per job order, e.g. `/cashier/job-orders/{jobOrder}/payment`)

Two stacked `Card` sections with `lg` (24px) gap, plus a conditional third:

**"Pricing" card** — editable while no `transactions` row exists yet for this job order; once at least one transaction exists, this card becomes a read-only summary (per Pattern 3's snapshot principle — never let a price change after money has moved):

- `Select` "Product / Service" — options from active `pricing_database` rows, labeled "{name} — ₱{base_price}"
- `Input type="number"` "Line Amount" — defaults to the picked catalog row's `base_price`, Cashier-editable (D-01's "manual adjust")
- `Switch` "Apply Rush Fee (+{rush_fee_percentage}%)" (D-03) — reads the live `rush_fee_percentage` system config, same read-pattern as every prior phase's config usage
- Discount `RadioGroup`: "None" / "Percentage" / "Flat Amount" (D-02); when not "None", show `Input type="number"` "Discount Value" with the "Up to {cap}" helper text reading the new discount-cap system config
- Computed breakdown (Body-role, read-only, updates live client-side for display only — the server recomputes and is authoritative on submit, per RESEARCH.md's "money math must be server-authoritative"): "Base Price", "Rush Fee", "Discount", then **"Total"** at Display size/weight
- No standalone "Save Pricing" button — pricing is submitted together with the first payment action below in one form, so the Cashier never has to save pricing and payment as two separate round-trips for the common case (full payment in one visit)

**"Payment" card:**

- `RadioGroup` "Payment Method": "Cash" (lucide `Banknote`), "Bank Transfer" (lucide `Landmark`), "GCash" (lucide `Wallet`), "Maya" (lucide `Smartphone`), "On Credit" (lucide `CreditCard`) — plain list rows exactly matching `NewVisit.vue`'s Type A/B pattern (icon + `Label`, no colored borders/cards, per the Color section's explicit "no brand colors" rule)
- `RadioGroup` "Payment Type": "Full Payment" / "Down Payment" (POS-05) — hidden entirely when "On Credit" is selected (D-09's credit path posts the full outstanding total, not a partial)
- Method-specific fields, shown/hidden based on the method radio (mirrors the demo's show/hide-by-method interaction, not its colors):
    - Cash: `Input type="number"` "Amount Tendered", live-computed "Change" display (Body-role) when tendered > total
    - Bank Transfer: `Input type="text"` "Bank Reference Number"
    - GCash / Maya: no amount input for Full Payment (amount = computed Total or the entered Down Payment amount); submitting transitions the page into the QR sub-view below rather than completing immediately
    - On Credit: no amount input (always the full outstanding total per D-09); submitting opens the "Request On-Credit Approval" `AlertDialog` per Copywriting Contract, then flashes the "credit requested" toast and returns to the Cashier Dashboard (§1) — no QR/receipt sub-view for this path
- Primary submit button, label per Copywriting Contract's contextual mapping (Cash/Bank Transfer full → "Record Payment"; any method down payment → "Record Down Payment"; GCash/Maya full → "Generate QR Code"; On Credit → "Request On-Credit Approval")
