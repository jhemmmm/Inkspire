<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| PayMongo servers → `webhooks/paymongo` | Fully untrusted network input, no session/CSRF, must be cryptographically verified before any DB write |
| Browser (Cashier) → PaymentController@store (GCash/Maya branch) | Cashier-initiated PayMongo API call; secret key never crosses to the browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-05-01 | Spoofing | `webhooks/paymongo` | mitigate | `luigel/laravel-paymongo`'s `PaymongoValidateSignature` middleware verifies the `Paymongo-Signature` header's HMAC-SHA256 against the raw request body before the controller runs; requests without a valid signature never reach `PaymongoWebhookController` |
| T-05-02 | Tampering / Repudiation | `ConfirmPaymentIntent` | mitigate | `lockForUpdate()` re-read + `status !== PendingConfirmation` guard inside `DB::transaction()` — a duplicate/replayed webhook delivery for an already-resolved transaction is a structural no-op, not merely a best-effort check |
| T-05-10 | Information Disclosure | PayMongo secret key (`sk_*`) | mitigate | Stored only in `.env` (untracked) via the package's own published config or `config/services.php`, following the existing `RESEND_API_KEY` pattern; never referenced from any `resources/js/**` file |
| T-05-11 | Denial of Service | Unrecognized `paymongo_payment_intent_id` in a webhook delivery | accept | Controller returns `200` with no DB write rather than erroring, so PayMongo doesn't retry indefinitely — accepted as intentionally permissive since it performs zero mutation for unrecognized intents |

</threat_model>
