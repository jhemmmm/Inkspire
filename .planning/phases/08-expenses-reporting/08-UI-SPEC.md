- `button` — every action trigger, the range presets, and (via `as="a"`) the two export links.
- `input` (`type="date"`, `type="number"`, `type="text"`) — the custom range fields and every expense form field. **No `calendar` / `popover` primitive is installed and none is added** — `PerformanceReport.vue` already proves the native date input is this project's date-picking contract.
- `label` — every form field caption.
- `select` — the expense category control (D-14's config-sourced options).
- `textarea` — the expense description field and the void-reason field.
- `dialog` — Record Expense, Edit Expense, and Void Expense.
- `alert` — the write-off disclosure callout and the voided-expense read-only notice.

No npm package is added. Two Composer packages (`barryvdh/laravel-dompdf`, `openspout/openspout`) are added under D-01's explicit approval; **neither ships any client-side asset, CSS, or component** — they are server-side renderers, invisible to the design system.

## Typography

### Screen surfaces

Unchanged 4-role scale from Phase 1-7 — reused as-is. **No fifth size, no third weight:**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.4 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

- **Body** — report card sub-lines, every preview table cell value, the range label and generated timestamp in the preview header, expense ledger cell values, dialog body copy, helper and footnote lines.
- **Label** — every table column header, every form field caption ("Category", "Amount", "Expense Date", "Description", "Reason", "From", "To"), all badge text, report card titles, summary figure captions.
- **Heading** — the preview panel's report title, the picker column's "Available Reports" caption, dialog titles, the financial summary's section headings ("Revenue", "Expenses", "Result").
- **Display** — page titles ("Reports", "Expenses"), the expenses ledger's total-for-range figure, and the financial summary's single **Net Profit / Net Loss** figure.

Display is applied to the one figure each surface exists to communicate — the same "the number that matters most" rule Phase 4 (performance stats), Phase 5 (receipt Total), Phase 6 (stage counts) and Phase 7 (Outstanding Balance) already set. On the financial summary, **Revenue, Expenses, and the write-off disclosure all stay at Body**, so Net Profit is the one figure that reads first. On a tabular report's summary strip, figures render at Heading, not Display — a strip of four equally-sized 28px numbers has no focal point and defeats the rule.

### PDF documents (a separate, declared print scale)

The four screen roles above govern **in-app screen surfaces only** — the same carve-out `07-UI-SPEC.md` made for the Laravel mail theme. A dompdf document is paged print media at physical point sizes, cannot load Instrument Sans (no `@font-face` registration is configured and none is added), and must stay legible at 100% on paper. It gets its own scale — still **4 sizes and 2 weights**, so the discipline is unchanged:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| PDF body / table cell | 9pt | 400 | 1.4 |
| PDF label / table header | 9pt | 700 | 1.3 |
| PDF document title | 14pt | 700 | 1.2 |
| PDF letterhead | 18pt | 700 | 1.2 |

`body { font-family: 'DejaVu Sans', sans-serif; }` is set explicitly in `resources/views/reports/layout.blade.php`. DejaVu Sans is dompdf's bundled default and is the font whose Unicode coverage includes **U+20B1 PESO SIGN (₱)**; leaving the family unset invites a substitution that drops the glyph.

**Binding verification step for the executor:** generate one PDF containing a peso amount and visually confirm the `₱` renders as the symbol and not as a tofu box or a blank. If it does not, the fix is to correct the font declaration — **never** to substitute the string `PHP ` for the symbol, which would make the PDF disagree with every screen and every printed receipt in the system.

### Money formatting contract

Phase 7's contract applies unchanged to every screen surface in this phase: `₱` + `Number(v).toLocaleString('en-PH', { minimumFractionDigits: 2, maximumFractionDigits: 2 })` inside a `tabular-nums` span, right-aligned in table cells. Existing Phase 5 surfaces keep their `toFixed(2)` formatting untouched.

**In PDF and `.xlsx` output the same value is formatted server-side**, not by re-implementing the JS helper:

- **PDF:** `'₱' . number_format($value, 2)`, right-aligned, in a `tabular-nums`-equivalent cell (`font-variant-numeric: tabular-nums`).
- **`.xlsx`:** the **raw numeric value** is written to the cell — no `₱`, no thousands separators, no string coercion. A spreadsheet column that a user can sum is the entire reason the `.xlsx` exists; writing `"₱12,340.00"` as text destroys it. This is a binding contract, not a preference.

### Date and time formatting contract

- **Dates on screen and in PDF:** `en-PH`, `{ month: 'short', day: 'numeric', year: 'numeric' }` → "Sep 10, 2026". Matches `QueueDisplay.vue` and the demo's `rpSetPreset` formatter.
- **Range label:** "Sep 1, 2026 – Sep 10, 2026" (en-dash, spaced). A single-day range collapses to one date: "Sep 10, 2026".
- **Generated timestamp:** `{ dateStyle: 'medium', timeStyle: 'short' }` → "Sep 10, 2026, 4:32 PM".
- **Dates in `.xlsx`:** ISO `YYYY-MM-DD` strings, for the same sortability reason the raw-number rule exists.

## Color

Extends, does not replace, the Phase 1-7 contract. **No new CSS custom properties, no new hex values in `resources/css/app.css`, no theme change, no chart palette.** Every treatment below is an existing token or one of the two already-established Tailwind utility overrides (green success from Phase 3-5, amber attention from Phase 6).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` | Page background — unchanged |
| Secondary (30%) | `--card` / `--muted` | Report picker cards, range-control panel, preview panel, expense summary cards, table header/zebra, the PDF's table header band (`--muted` equivalent, `#f5f5f5`) — unchanged |
| Accent (10%) | `--primary` | Reserved for: existing Phase 1-7 list, **plus** the four primary submit buttons this phase introduces ("Apply Range", "Record Expense" confirm, "Save Changes" in the edit dialog, and the "Record Expense" page CTA), the **active** preset range button (`variant="default"`, inactive siblings `variant="outline"` — the same active-filter treatment Phase 6 gave its stage tabs), and the selected report card's `border-primary` indicator. Never a decorative fill. |
| Destructive | `--destructive` | Reserved for: existing Phase 1-7 list, **plus** the "Void Expense" dialog trigger and its confirm button, and the **Net Loss** figure when the financial summary's result is negative. Nothing else in this phase. |

### The three colour decisions this phase has to get right

**1. A negative result is the one new destructive use, and it is never colour-alone.** When revenue minus expenses is below zero, the figure renders `text-destructive`, its caption changes from "Net Profit" to **"Net Loss"**, and the amount carries an explicit leading minus sign. A colour-blind user, a greyscale printout, and a screen reader each get the meaning from the word and the sign. When the result is zero or positive it renders in default foreground — **never green.** Phase 7's rule holds: a normal state does not get a colour.

**2. The write-off disclosure line is NOT destructive-coloured.** D-09 makes it a disclosure that is deliberately *not* deducted. Colouring it red reads as "this was subtracted and it hurt", which is the exact misreading D-09 exists to prevent. It renders at Body in `text-muted-foreground`, visually subordinate to the Revenue/Expenses/Result block, inside an `Alert` (default variant, lucide `Info`) whose copy states the non-deduction in words. See §Copywriting Contract for the exact string.

**3. Report rows inherit their existing badge mappings verbatim — this phase invents no new status colour.** A Sales row's `payment_method`, a Production Status row's `JobOrderStatus`, a Cancellation row's `payment_status`, an Expenses row's category — each renders with the treatment its owning phase already defined (`03-UI-SPEC.md` / `04-UI-SPEC.md` job order status, `05-UI-SPEC.md` payment status, `07-UI-SPEC.md` written-off and aging). A report is a view over existing data; it must look like the data it reports on.

**Demo behaviour explicitly rejected:** `rpPreview` colour-codes every cell by string matching (`c.includes('Rush')` → warning, `c.includes('90+')` → error, any cell containing `₱` → mono). Three problems: it applies colour by substring accident rather than by semantics, it puts four competing colours in one table body, and it would silently disagree with the badge mappings Phases 3–7 established for the same values. **Report cells render plain; status values render as the existing `Badge` component for that field.**

### Expense status badge — one new treatment

| State | Display label | Badge treatment | Meaning |
|---|---|---|---|
| active (not voided) | *no badge rendered* | — | The normal state of every row. A badge on every row carries no information. |
| voided | "Voided" | `variant="outline" class="text-muted-foreground"` | Closed and inert — the row survives for the audit trail but counts toward nothing. **Never `variant="destructive"`**: a voided expense is a correction, not an error. Identical treatment to Phase 7's "Written Off" badge, so the system's two "closed, not deleted" states agree on sight. |

**Accent reserved for:** the additions listed in the table above only. Never used for decorative fills — same rule as every prior phase.

**The PDF carries no colour at all.** Black text, `#f5f5f5` table header band, `#dddddd` rules. Reports are printed, photocopied, and faxed; every meaning must survive greyscale. The Net Loss case is carried in the PDF by the "Net Loss" caption and the minus sign, not by red ink.

### Toasts (`Inertia::flash('toast', …)` — existing convention)

**No toast fires on export, and this is deliberate.** An export is a plain browser navigation, not an Inertia visit — there is no response for the toast listener to read, and a click-time optimistic toast saying "exported successfully" would lie whenever the server returns a 403 or an error. The static export helper line ("Exports carry every row in this range and are recorded in the audit trail.") carries the same reassurance honestly, and the browser's own download indicator is the completion signal.

**Demo behaviour explicitly rejected:** `rpExport`'s two-stage toast (`Exporting "{title}" as PDF…` → `"{title}" exported successfully!`). It is a stub with no file behind it; its success message is unconditional. CONTEXT.md's `<specifics>` offers it as a model for the **audit entry text**, and that is the only place it is reused: the D-02 audit action reads `Report exported — {title} ({format})` with the date range in the payload.

### Destructive confirmation

**This phase introduces exactly one destructive action: voiding an expense.** It is the only irreversible act here — no unvoid path exists, and a voided row is permanently excluded from every report.

- **"Void Expense" (Accounting Staff)** — a plain `Dialog` (not an `AlertDialog`) with a required `Textarea` and a `variant="destructive"` confirm button; the row trigger is `variant="outline"` with the lucide `Ban` icon and destructive text (`class="text-destructive"`). The `Dialog` choice follows Phase 7's "Request Write-Off" precedent exactly: a confirmation that must collect a mandatory reason is a form, and an `AlertDialog`'s action button is not form-bound. The destructive confirm colour and the "This can't be undone" sentence carry the warning that the primitive would otherwise carry.
- **"Edit"** — a plain `Dialog` with a `--primary` confirm. Correcting a typo is the ordinary case D-11 exists to serve, not a warning moment. The dialog description names the one real consequence (an already-printed report will differ) without blocking the action.
- **"Record Expense"** — a plain `Dialog` with a `--primary` confirm. No confirmation step.
- **"Apply Range"**, **"Export PDF"**, **"Export Excel"**, report card selection — plain actions, no confirmation. Reading data is never gated behind a confirmation.
- **"Download Letter (PDF)"** — plain navigation, no confirmation, matching the existing "Print Collection Letter" button beside it.

## Phase-Specific UI Notes

**Two new surface families, one new Blade document family, three bounded extensions. Do not build anything beyond these.**

### 1. Shared Reports workspace (four thin pages + one shared component)

**This settles `08-RESEARCH.md` Open Question 2.** D-04 locks one registry, one range control, one export pipeline — it does not name a file count. The project's `app.ts` resolves layouts by page path and every page supplies its own `defineOptions({ layout: { navItems, breadcrumbs } })`, so a single `.vue` rendered from four route namespaces cannot carry four different sidebars.

**Contract:**

- `resources/js/components/reports/ReportsWorkspace.vue` (new) — **all** of the layout, range control, picker, preview, and export markup lives here, taking `reports`, `selected`, `rows`, `summary`, `filters`, and the two export URLs as props.
- `resources/js/pages/owner/Reports.vue`, `cashier/Reports.vue`, `production-staff/Reports.vue`, `accounting-staff/Reports.vue` (new, four files) — each is a thin wrapper: its own `<Head>`, its own `defineOptions` layout block with that role's nav items and breadcrumbs, its own sub-copy string, and `<ReportsWorkspace v-bind="$props" />`. **Nothing else.** If a role-specific `v-if` appears in one of these four files, the entitlement boundary has leaked to the client and the contract is broken.

**Layout — master/detail, `lg` (24px) gaps:**

```
H1 "Reports" (Display) + role sub-copy (Body, muted)
grid gap-6 xl:grid-cols-[300px_minmax(0,1fr)]
├─ LEFT: "Available Reports" (Heading) + a stacked column of report Cards, md (16px) gap
└─ RIGHT:
   ├─ Date Range Card — preset Button row (sm/8px gap) + From/To Inputs (Custom only) + "Apply Range"
   └─ Preview Card — title/sub/range/generated header + export Buttons + summary strip + Table
```

Below `xl` the two columns stack, picker first. The picker is a plain vertical list of cards on every breakpoint — never a horizontal scroller, which hides options off-screen on exactly the laptop widths this shop uses.

**Report picker cards.** Each card renders the registry title (Label), sub-line (Body, muted), and category `Badge variant="secondary"`. The card is a real `<button type="button">` with `aria-pressed`, not a `<div @click>` — the Phase 7 rule against unreachable click targets applies here too. The selected card carries `border-primary` and an `sr-only` "Selected". Selecting a report is an Inertia `router.get` with `{ preserveState: true, preserveScroll: true, replace: true }`, carrying the current range forward — **the range never resets when the report changes.**

**Default selection: the first report in the role's entitled list, auto-selected on page load.** Reasons: Production Staff has exactly one report and must not be made to click a list of one to see it; an empty preview panel on arrival looks like a broken page; and it means the "no report selected" state does not exist and does not need copy. The registry order is the order in §Copywriting Contract's registry table.

**The range control.** Five preset `Button`s (`sm`/8px gap), the active one `variant="default"` and the rest `variant="outline"`. Choosing a preset applies immediately (one Inertia visit, no second click). Choosing "Custom" reveals the two `Input type="date"` fields plus the "Apply Range" submit — the exact `PerformanceReport.vue` form shape, extended with presets. The resolved range renders as "Showing {range label}" beneath. **Presets are computed client-side and submitted as concrete `from`/`to` dates**, never as a preset name — the server validates two dates and nothing else, which keeps `FilterReportRequest` identical to the existing `PerformanceReportFilterRequest`.

**Preview table.** shadcn `Table`, columns per the registry, money right-aligned `tabular-nums`, status values as their existing `Badge`s. **Capped at 100 rows** with the `TableFooter` line from the Copywriting Contract; **no pagination control.** Reasons: a second navigation axis beside the date range doubles the state the user holds; the export is the complete-set answer and the footer says so; and a paginated preview invites the belief that the export is paginated too. `TableEmpty` for every empty state.

**Export buttons.** `<Button as="a" :href="…url()" variant="outline">` — a real anchor, never `<Link>` or `router.visit()`, because Inertia's XHR machinery cannot receive a `Content-Disposition: attachment` response (`08-RESEARCH.md` Pitfall 3 / the Inertia download pattern). The `href` comes from the Wayfinder `.url()` helper with the current `from`/`to` in the query — no hardcoded URL strings. **No `target="_blank"`**: a download response replaces nothing, and an orphan blank tab is left behind on every export.

**`financial-summary` renders the figure block instead of a `Table`** — same panel, same header, same export buttons, different body. This is the one registry entry whose preview is not a row table.

**No polling, no auto-refresh, no live timestamp.** The "Generated {timestamp}" line is stamped by the server on the response that produced the rows; it must not tick.

### 2. One registry entry serves both RPT-01 and RPT-04's Summary

CONTEXT.md left this open and asked for one decision, not a third variant. **Decision: one entry, `financial-summary`, titled "Summary of Sales & Expenses", entitled to Owner and Accounting Staff, showing byte-identical content to both.**

Reasons: it is the same query (D-08 revenue less D-13 expenses); the write-off disclosure is arguably *more* relevant to Accounting, who own the AR lifecycle, than to the Owner; and D-10's revenue split costs nothing to show twice. Building a reduced Accounting variant would create exactly the third variant CONTEXT.md forbids.

**Binding:** there is no role-conditional content anywhere inside this report. If a future requirement genuinely needs Accounting to see less, that is a new registry entry, not a `v-if`.

### 3. Expenses ledger (`resources/js/pages/accounting-staff/Expenses/Index.vue`, new — one file)

One page, three dialogs, no separate create or edit route. This follows `owner/CreditRequests.vue` and `accounting-staff/AccountsReceivable/Index.vue`'s established shape (a list with per-row dialog actions), not a `Create.vue` / `Edit.vue` pair — `08-RESEARCH.md`'s structure sketch offers both and this settles it.

Top to bottom, `lg` (24px) gaps:

- **H1** "Expenses" (Display) + sub-copy (Body, muted), with the "Record Expense" primary CTA right-aligned on the same row.
- **Range control** — the *same* preset control as §1, so the two surfaces behave identically. Same default ("This Month"). Extract it as `resources/js/components/reports/DateRangeControl.vue` and use it in both places; two divergent date pickers in one phase is the kind of drift this contract exists to prevent.
- **Summary `Card`** — the range total at Display, "{n} expenses" beneath at Body, and the voided-excluded sub-line when applicable. One card, not a row of four: there is exactly one number here.
- **Ledger `Table`** — columns per the Copywriting Contract, newest expense date first, money right-aligned `tabular-nums`, `TableEmpty` for both empty states. Voided rows keep full contrast (**never `opacity`-dimmed** — the Phase 7 rejection of the demo's `opacity:0.55` applies verbatim); the "Voided" badge plus the muted reason line beneath the description carry the state.
- **Rows are not clickable.** Same rule as every list in this app.
- **No pagination in this phase.** A single-location shop records tens of expenses a month and the range control already bounds the set. If the ledger later needs it, `01-UI-SPEC.md`'s existing pagination pattern is the one to reach for — do not invent a second.

**Owner does not get an expenses page.** D-12 requires the Owner to *read* the itemized list; the `expenses` report on the shared Reports workspace **is** that list, with the same columns. Building a read-only Owner mirror of this page would duplicate a surface and create a second place for the two views to disagree.

### 4. PDF documents (`resources/views/reports/`, new — the first Blade documents in this app)

Isolated under `resources/views/reports/` per D-01, and **never rendered to a browser as a page**. The screen is Inertia; the file is Blade. If a Blade view in this directory is ever returned from a `Route::get` as an HTML response, the boundary has been broken.

- `layout.blade.php` — the shared shell: A4 portrait, 18mm margins, DejaVu Sans, the text letterhead, the document title, the two meta lines, a `@yield('content')`, and the paged footer. **The collection-letter PDF extends this same layout** (D-03), so the shop's demand letter and its reports carry one identity.
- One view per registry key + `collection-letter.blade.php`.
- **Every interpolation uses `{{ }}`, never `{!! !!}`.** Customer names, expense descriptions, and void reasons are user-supplied strings landing in a rendered document — `08-RESEARCH.md` §Security flags this as the phase's one output-handling risk.
- Table styling: `#f5f5f5` header band, `#dddddd` 1px rules, no zebra striping (it photocopies as mud), `page-break-inside: avoid` on rows.
- No colour, no badges, no icons. A PDF status value renders as its plain label text.

### 5. `.xlsx` exports

The sheet mirrors the on-screen table for that report: row 1 = the same column headers, rows 2..n = the same rows in the same order, final row = the totals row from the Copywriting Contract. Money cells carry raw numbers, dates carry ISO strings, status values carry their plain display labels. `financial-summary`, whose on-screen shape is a figure block rather than a table, exports as a two-column **Label / Amount** sheet in the same top-to-bottom order the block reads, with the write-off disclosure as its own labelled row at the bottom — its non-deduction stated in the label text, since a spreadsheet has no `Alert`.

**No formatting, no merged cells, no frozen panes, no styling of any kind.** CONTEXT.md prefers raw rows and this confirms it: openspout streams rows, and every added flourish is a memory cost and a v4/v5 API risk (`08-RESEARCH.md` Pitfall 4) for zero requirement.

### 7. Entitlement is invisible in the UI, by design

D-04 makes the server the single boundary. The client-side consequences are binding:

- The `reports` prop contains **only** the entitled entries for the authenticated user. The full registry is never serialized to the client.
- **No `v-if` anywhere filters a report by role.** The four thin page files contain no role checks (§1).
- A non-entitled role reaching a report or export URL directly gets the existing 403 error page (`resources/js/pages/errors/Forbidden.vue`, Phase 1) — **not** an empty preview, not a friendly "you don't have access to this report" panel inside the Reports page. This phase adds **no new error surface**; RBAC-02's established 403 is the answer.
- Admin has no Reports nav item and no Reports route. There is no "no reports available to you" empty state, because no entitled role can reach one.
