## Color

Extends, does not replace, Phase 1/2's contract. No new hex values or CSS custom properties introduced — every mapping below reuses existing `--primary` / `--destructive` / green-success tokens already established in Phase 2's queue-status badges.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` | Page background — unchanged |
| Secondary (30%) | `--card` / `--muted` | Card containers, table zebra/header — unchanged |
| Accent (10%) | `--primary` | Reserved for: primary submit buttons (unchanged list from Phase 2), **plus** the "Assigned" job order status badge (`Badge variant="default"`) — an artist has been actively routed to this job, the same "currently being handled" semantic Phase 2 gave the "Serving" queue badge |
| Destructive | `--destructive` | Reserved for: existing Phase 1/2 list, **plus** the "Validation Failed" job order status badge (`Badge variant="destructive"`) and the failure-reason `Alert variant="destructive"` — both are error states, not user-triggered destructive actions, matching the exact precedent Phase 1 already set for the account-lockout status badge |

**Job order status badge mapping (new this phase — extends the existing Queue-status badge pattern from `QueueList.vue`, does not replace it; queue-entry status and job-order status are two different fields on two different models and must never be visually conflated):**

| `JobOrderStatus` value | Display label | Badge treatment | Meaning |
|---|---|---|---|
| `intake` (Type B, no artist available yet — D-07) | "Awaiting Assignment" | `variant="outline"` | Not yet actionable — mirrors the exact treatment Phase 2 gave "Waiting" |
| `ready_for_production` (Type A passed validation — D-08) | "Ready for Production" | `class="text-green-600 dark:text-green-400"` (no `variant` prop, matching Phase 2's "Done" badge exactly) | Successfully resolved, no action needed |
| `assigned` (Type B auto-assigned — D-08) | "Assigned" | `variant="default"` | Actively routed to an artist — mirrors "Serving" |
| `validation_failed` (Type A failed validation — D-02/D-09) | "Validation Failed" | `variant="destructive"` | Error state, requires Frontline Staff action |

Note: raw `intake` is only ever visibly rendered for a Type B job order with zero available artists (D-07). Per D-03, Type A validation runs synchronously in the same request that stores the file, so a Type A job order's status is **always** already `ready_for_production` or `validation_failed` by the time any page renders it — the UI never needs to render a "Type A, still processing" transitional state.

Accent reserved for: the additions above only, still never used for decorative fills — same rule as Phase 1/2.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (this phase's one new interactive element) | "Replace File" |
| Job order status badge labels | "Awaiting Assignment" / "Ready for Production" / "Assigned" / "Validation Failed" (exact mapping and treatment above — never render the raw enum value) |
| Assigned-artist indicator (secondary text under an "Assigned" job order row) | "Assigned to {artist_name}" |
| Failure reason — DPI too low | "Image resolution is {actual} DPI. Minimum required is {minimum} DPI. Replace the file with a higher-resolution version." |
| Failure reason — unsupported format | "File format \".{extension}\" isn't accepted. Accepted formats: {accepted_formats}. Replace the file with a supported format." |
| Failure reason — over size limit | "File is {actual}MB, which exceeds the {max}MB limit. Replace the file with a smaller version." |
| Replace File dialog title | "Replace File" |
| Replace File dialog field label | "New File" |
| Replace File submit button | "Replace File" |
| Toast — Add Job Order dialog result, Type A passed | "Job order added — ready for production." |
| Toast — Add Job Order dialog result, Type A failed | "Job order added — file needs replacement. See details in the queue list." |
| Toast — Add Job Order dialog result, Type B assigned | "Job order added — assigned to {artist_name}." |
| Toast — Add Job Order dialog result, Type B unassigned | "Job order added — awaiting an available artist." |
| Toast — file replaced, passed validation | "File replaced. Job order is ready for production." |
| Toast — file replaced, still fails validation | "File replaced, but validation failed again. See the updated reason below." |

**Destructive confirmation:** none. "Replace File" is a corrective action on an already-invalid file, not a destructive one — same reasoning Phase 1 already applied to the non-destructive "Reactivate" action (01-11: "no `AlertDialog` confirmation — non-destructive, corrective action"). Do not wrap it in `AlertDialog`; use the same plain `Dialog` + `Form` shell as the existing "Add Job Order" dialog.

**Empty state:** not applicable this phase. This phase adds no new list/page and no new zero-result view — every list it touches (`NewVisit.vue`'s confirmation card, `QueueList.vue`'s table) already has its empty-state contract defined in `02-UI-SPEC.md`, unchanged here.

## Phase-Specific UI Notes

**Two surfaces only — do not build anything beyond these:**

**Visual hierarchy:** within any job order row, the `validation_failed` Alert + "Replace File" button pairing is the primary visual anchor — it sits ahead of the neutral status badges in scan order, since it's the one state that demands Frontline Staff action.

**1. `NewVisit.vue` confirmation card (`confirmedQueueEntry.job_orders` list) — the primary surface, since D-03 makes validation/assignment outcomes available in the very same response that renders this card:**
- Each `<li>` job order row (already showing description + Type A/B `Badge`) gets a new status `Badge` appended, per the mapping above.
- When status is `assigned`: add the "Assigned to {artist_name}" secondary text line (`text-muted-foreground text-sm`, same treatment already used for the customer contact/email lines in the "Customer" card above it) — requires the backend prop to include the assigned artist's name on the job order payload.
- When status is `validation_failed`: render the `AlertError.vue` component directly below that `<li>` (reuse as-is, pass `:errors="[jobOrder.failure_reason]"`, default title "Something went wrong." is acceptable or override `title="Validation Failed"`), followed by a "Replace File" `Button` (`variant="outline"`, `size="sm"`) that opens a `Dialog`.
- The Replace File `Dialog` mirrors `QueueList.vue`'s existing "Add Job Order" dialog shell exactly: `DialogHeader`/`DialogTitle` ("Replace File"), a single `Label` + `Input type="file"` field ("New File"), `InputError` for `errors.file`, `DialogFooter` with `DialogClose` "Cancel" (`variant="secondary"`) + submit "Replace File" button (`:disabled="processing"`).

**2. `QueueList.vue` table — the durable/return-visit surface, since a Frontline Staff member may navigate away before fixing a `validation_failed` job order and need to find it again later:**
- Add a new "Job Orders" column (between "Customer" and "Status", before the queue-entry-level "Status"/"Actions" columns — queue-entry status and job-order status must stay visually distinct, never merged into one column or one badge).
- Each queue entry's job orders render as a compact stacked list inside that cell: description text + Type A/B `Badge` (`variant="outline"`, existing convention) + the new status `Badge`, all on one line, wrapping to a second line only for the `validation_failed` case's inline "Replace File" `Button` (`variant="outline"`, `size="sm"`, icon-only acceptable using lucide `Upload`/`RefreshCw` with `sr-only` "Replace File" text — same icon-button pattern already used for the "Add Job Order" `Plus` icon button in this file).
- The Replace File dialog triggered from this table is identical in shape to the one in `NewVisit.vue` above — same `Dialog`/`Form`/`DialogFooter` shell, just scoped to a specific `jobOrder.id` instead of being inline with the just-created confirmation.
- On successful replace-file submit (regardless of pass/fail outcome), close the dialog and show the corresponding toast from the Copywriting Contract above (`Inertia::flash('toast', ...)` — existing convention) rather than leaving the dialog open; the table's status badge updates from the reloaded Inertia props exactly as `QueueList.vue`'s existing "Call Next"/"Mark Done" actions already do via `preserveScroll: true`.

**Out of scope for this UI-SPEC (confirmed via `routes/portals.php` — the `artist` role group is still an empty dashboard stub with zero job-order routes):**
- No Artist-facing job-order list, no "assigned jobs" view, no On Break/End Shift toggle UI — all of that is JOB-08/JOB-09, Phase 4.
- No new nav item — `frontline-staff.ts`'s existing three items (Dashboard, New Visit, Queue) already cover both surfaces above; do not add a fourth.
- No dedicated "Validation Failed" filter/report view — not requested in CONTEXT.md's decisions; if Frontline Staff needs to triage failures shop-wide later, that's a future-phase reporting concern, not this one.
