### Gaps Summary

**What 07-08 actually fixed (confirmed, not just claimed):** all 6 of the mutators it pre-enumerated (`CreditRequestController`, `CreditApprovalController`, `WriteOffApprovalController`, `ConfirmPaymentIntent`, `CollectionStatusController`, `CollectionLetterController`) now share the same locked-re-read/terminal-guard discipline, confirmed by direct code read of every one of them — genuinely ending the specific "next round finds the neighbouring unguarded file" pattern for that enumerated set. The full 456-test suite is green with zero failures, matching the claimed numbers exactly.

**What is still not achieved, found by this round's independent verification of the fresh code review's claims (not inherited severity — verified against the code directly):**

1. **`PaymentController::store()` — the highest-traffic payment_status mutator in the entire system — has no locked re-read.** It sat outside 07-08's 6-mutator enumeration because its `abort_if` guards already existed and looked sufficient from the outside; but those guards run once, unlocked, before the `DB::transaction()`, and the transaction closure reuses that same unlocked instance rather than re-fetching under lock. This is the identical bug class the last three gap-closure rounds each closed for a different mutator (CollectionStatusController this round, CreditApprovalController this round, WriteOffApprovalController two rounds ago, CreditRequestController two rounds ago) — now confirmed present in the one mutator none of them targeted. This directly fails AR-04's "stable, correct terminal state" bar for a fourth time.

2. **`JobOrder::outstandingBalance()` — the very method 07-08 built specifically to make future guard-writing easier — commingles `CancellationFee` transactions with real debt payments**, because `CancellationController::store()` does not block cancelling an `OnCredit` job order. This is a correctness defect (not a missing-lock race) that reaches every single AR-01/02/03/04 surface simultaneously, since they were all just centralized onto this one method: the aging list can under-report a balance, a reminder email can understate what's owed, a collection letter can print the wrong amount due, and — most acutely for AR-04 — both `WriteOffApprovalController::approve()` and `CreditApprovalController::approve()`'s settlement guards can act on an incorrect number.

**Overall assessment:** AR-01, AR-02 stand functionally verified with a shared, confirmed balance-accuracy caveat (CR-02) that does not break the feature but does undermine the numbers it displays. AR-03's two integrity gaps from the prior round (old CR-03/CR-04) are both genuinely closed this round.
