## Typography

Unchanged 4-role scale from Phase 1-6 — reused as-is. **No fifth size, no third weight:**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.4 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

- **Body** — aging table cell values, due dates and their past-due sub-lines, activity log entries, dialog body copy, collection letter body paragraphs, reminder email body lines.
- **Label** — table column headers, bracket summary card captions, "Collection Status" / "Reason" field labels, all badge text, filter tab labels, entry-detail field captions ("Approved On", "Due Date", "Days Past Due").
- **Heading** — entry-detail panel headings ("Amounts", "Collection Status", "Activity"), dialog titles, the collection letter's "Statement of Account" title.
- **Display** — page titles ("Accounts Receivable", "Write-Off Requests"), each bracket card's peso total, the entry-detail **Outstanding Balance** figure, and the collection letter's **Amount Due** figure and letterhead name.

Display is applied to the money figure that the surface exists to communicate — the same "the number that matters most" rule Phase 4 (performance stats), Phase 5 (receipt Total) and Phase 6 (stage counts, public stage label) already set. It is **not** applied to every peso amount: Total and Paid on the entry-detail Amounts panel stay at Body, so Outstanding is the one figure that reads first.

**Money formatting contract (new, phase-scoped):** peso amounts on this phase's surfaces render as `₱` + `Number(v).toLocaleString('en-PH', { minimumFractionDigits: 2, maximumFractionDigits: 2 })` inside a `tabular-nums` span, right-aligned in table cells. Thousands separators are introduced here because AR sums run to six figures and a bracket total is meant to be scanned, not read digit by digit — this matches the demo's `acFmt` helper. **Existing Phase 5 surfaces keep their `toFixed(2)` formatting untouched** — retrofitting them is out of scope for this phase and must not be attempted.

Extends, does not replace, the Phase 1-6 contract. No new CSS custom properties, no new hex values in `resources/css/app.css`, no theme change. Every treatment below is either an existing token (`--primary`, `--secondary`, `--destructive`, `--muted-foreground`) or one of the two already-established Tailwind utility overrides (green success from Phase 3-5, amber attention from Phase 6).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` | Page background — unchanged |
| Secondary (30%) | `--card` / `--muted` | Bracket summary cards, entry-detail panels, table header/zebra, collection letter card — unchanged |
| Accent (10%) | `--primary` | Reserved for: existing Phase 1-6 list, **plus** the three primary submit buttons this phase introduces ("Update Status", "Submit Request" inside the write-off dialog, "Reject Request" confirm in the Owner queue), the active bracket filter tab, and the "Collections" collection-status badge (the existing "needs attention" badge tier from Phase 5). | Destructive | `--destructive` | Reserved for: existing Phase 1-6 list, **plus** the "90+ Days" aging badge and the Owner's "Approve Write-Off" trigger + confirm button. Nothing else in this phase. |

### Aging bracket palette (AR-01) — the one new colour axis

Six brackets cannot each get a colour without turning the table into a rainbow. The rule is **three semantic tiers over six brackets**, reusing treatments that already exist:

| Bracket | Display label | Badge treatment | Why this tier |
|---|---|---|---|
| `Current` | "Current" | `class="text-green-600 dark:text-green-400"` (no `variant` prop — the existing "Paid" / "Done" success precedent) | Not yet due. Nothing is wrong. |
| `1–15` | "1–15 Days" | `variant="secondary"` | Past due, being worked. Same "in progress" tier as `in_consultation` / `pending_confirmation`. |
| `16–30` | "16–30 Days" | `variant="secondary"` | Same tier, distinguished by label text only. |
| `31–60` | "31–60 Days" | `variant="outline" class="text-amber-600 dark:text-amber-400 border-amber-600/40"` | Needs attention now — reuses Phase 6's amber urgency utility verbatim. |
| `61–90` | "61–90 Days" | Same amber treatment | Same tier, distinguished by label text only. |
| `90+` | "90+ Days" | `variant="destructive"` | The write-off candidate. This is the only bracket where the system itself asks for a decision (D-06's final escalation), so it is the only one that earns `--destructive`. |

**No collision with Phase 6's urgency axis.** Phase 6 warned that green/amber on a production card would fight the Rush/Normal meaning. The AR surfaces carry no urgency axis at all — there is no Rush badge, no due-date SLA colour, and no production data on any Phase 7 page — so amber and green are free to mean "attention" and "fine" here without ambiguity.

**Accessibility rule (binding):** the aging bracket is **never encoded by colour alone**. Every badge carries its literal label ("31–60 Days"), and every row additionally shows the numeric "{n} days past due" sub-line under the due date. A colour-blind user or a greyscale print reads the words and the number.

### Collection status: explicitly NOT colour-scaled

The demo gives collection status its own five-colour palette (`acStatusBadge`: neutral / primary / warning / error / success) on the same row as its aging palette. Two independently coloured axes in one row is exactly the collision Phase 6 resolved by declaring "urgency owns colour; stage does not."

**Resolution (this UI pass's call): aging owns colour; collection status is monochrome, with two exceptions for terminal states that carry no aging meaning at all.**

| `collection_status` value | Display label | Badge treatment | Meaning |
|---|---|---|---|
| `pending` | "Pending" | `variant="outline"` | Nobody has worked it yet — mirrors "Unpaid" / "Awaiting Assignment" |
| `follow_up` | "Follow-up" | `variant="secondary"` | Being worked |
| `warning_sent` | "Warning Sent" | `variant="secondary"` | Being worked, distinguished by label text only |
| `collections` | "Collections" | `variant="default"` | Needs attention now — the Phase 5 "needs attention" badge tier (`--primary` fill) |
| `paid` | "Paid" | `class="text-green-600 dark:text-green-400"` | Terminal, system-set (D-10) |
| `written_off` | "Written Off" | `variant="outline" class="text-muted-foreground"` | Terminal, system-set. Closed and inert — not an error, so **never `variant="destructive"`**. The muted foreground is what distinguishes it from plain `outline` "Pending". |

**Demo behaviour explicitly rejected:** `acRenderDashboard` dims written-off rows with `opacity:0.55`. Opacity dimming pushes body text below WCAG contrast and is not reused — the muted badge plus the "Closed" tab (§1) carry that meaning without degrading legibility.

**Outstanding balance is never coloured red.** The demo tints any non-zero balance with `var(--error)`. An unpaid balance is the normal state of every row on this page; colouring all of them red makes `--destructive` meaningless. Outstanding renders in default foreground; a settled (zero) balance renders in the green success utility with the word "Settled" beside it.

### `payment_status` badge mapping — one new case (D-14)

Extends Phase 5's table. Every other `payment_status` mapping stays exactly as `05-UI-SPEC.md` defined it.

| `PaymentStatus` value | Display label | Badge treatment | Meaning |
|---|---|---|---|
| `written_off` (new) | "Written Off" | `variant="outline" class="text-muted-foreground"` | Terminal closed state — the balance was forgiven, not collected. Identical treatment to the `collection_status` badge of the same name, so the two agree on sight. |

**Regression rule (binding, per `07-RESEARCH.md` Pitfall 4):** `resources/js/pages/cashier/Dashboard.vue` and `resources/js/pages/frontline-staff/Dashboard.vue` both branch on `payment_status` through an exhaustive `v-if` / `v-else-if` chain with **no `v-else` fallback**, and their `paymentStatusLabel()` switches have no reachable `default`. Both must gain a `written_off` branch and label in the same commit that adds the enum case. A written-off order rendering a blank payment cell is a Phase 7 defect, not a Phase 5 one.

**Accent reserved for:** the additions listed in the table above only. Never used for decorative fills — same rule as every prior phase.

### Destructive confirmation

**This phase introduces exactly one destructive action: the Owner's write-off approval.** It is the only irreversible act here — it closes a receivable as a loss and stamps a terminal `payment_status` that no other flow reverses.

- **"Approve Write-Off" (Owner)** — `AlertDialog`, trigger and confirm button both `variant="destructive"`, copy per the table above. **This deliberately inverts the polarity of `CreditRequests.vue`**, where "Approve Credit" is primary and "Reject Credit" is destructive. The reason is that the polarity of harm is inverted too: rejecting a credit request strands a customer at the counter, while rejecting a write-off request merely resumes normal chasing. Approving a write-off is the action that permanently gives up money. The colour follows the irreversibility, not the word "approve".
- **"Reject Request" (Owner)** — `AlertDialog` with a default (`--primary`) confirm button and a `variant="outline"` trigger. Non-destructive and corrective: the entry returns to unflagged Active and keeps aging. Same reasoning as Phase 1's "Reactivate has no destructive styling" precedent.
- **"Request Write-Off" (Accounting)** — a plain `Dialog`, **not** an `AlertDialog`, with a `--primary` confirm button. It exists to collect D-13's mandatory reason, not to warn, and an Owner rejection reverses it completely. This follows Phase 6's "Send Back" dialog precedent exactly.
- **"Update Status"** — a plain `Button` inside an Inertia `<Form>`, no confirmation. A record of human activity, freely reversible in any direction (D-10).
- **"Print Collection Letter"** — plain navigation, no confirmation.

## Phase-Specific UI Notes

**Four new surfaces, one new email template, two bounded extensions. Do not build anything beyond these.**

### 1. Accounts Receivable aging list (`resources/js/pages/accounting-staff/AccountsReceivable/Index.vue`, new)

**Layout decision (CONTEXT.md delegated this to the UI pass): bracket summary cards over a tab-filtered table — the demo's shape, with its filter controls trimmed.** Reasons, in order of weight:

1. **AR-01 asks for two things in one sentence** — "view outstanding balances" (the rows) "grouped into aging brackets" (the summary). Cards answer the grouping question at a glance; the table answers the per-account question. A table alone forces the reader to add up brackets by eye.
2. **The cards carry money, not counts.** Each card shows the bracket's **total outstanding peso amount** at Display size, with "{n} entries" as a muted sub-line. This is a deliberate departure from Phase 6's count-only stat cards: a production board counts jobs, an aging report totals money, and "₱182,400 in 90+ Days" is the number that drives the write-off conversation.
3. **House consistency.** Every internal list surface in this app is a shadcn `Table` (`QueueList.vue`, `AuditTrail.vue`, `CreditRequests.vue`, both dashboards), and Phase 6 already established `Tabs` as this project's filter control.

Page structure, top to bottom, `lg` (24px) gaps:

- **H1** "Accounts Receivable" (Display) with the sub-copy line beneath (Body, `text-muted-foreground`).
- **Six bracket `Card`s** in `grid grid-cols-2 gap-4 md:grid-cols-3 xl:grid-cols-6`. Caption at Label, peso total at Display, "{n} entries" at Body muted. **Cards are display-only, not clickable** — the tabs are the single filter affordance, and two competing filter mechanisms on one page is a worse problem than one extra click.
- **Bracket filter `Tabs`** — `TabsList` carries `class="h-auto flex-wrap"` so eight triggers wrap instead of overflowing on a laptop. **Client-side filtering over the already-fetched array** (a single-location shop's Active AR count is dozens, per PROJECT.md's scale framing): no query param, no server round-trip.
- **Aging `Table`** — columns per the Copywriting Contract. Default sort: most overdue first (`due_at` ascending), then by outstanding amount descending. Money columns (`Total`, `Paid`, `Outstanding`) are right-aligned `tabular-nums`. `TableEmpty` for every empty state.
  - **Actions cell** — one `variant="outline" size="sm"` "View Entry" button linking to §2. **Rows are not clickable.** The demo makes the entire `<tr>` an `onclick` target with a hover tint; that is unreachable by keyboard and unannounced by screen readers, and no existing page in this app does it.
- **No polling.** Phase 6's `usePoll(5000)` is deliberately **not** carried over — aging brackets advance once a day at most, and reminders are sent by a scheduled command, not by anyone watching this page. A 5-second poll here would be pure noise.

**The "Closed" tab, and what the bracket cards count (this UI pass's call — CONTEXT.md left it open).** D-01 filters the list to `status = Active`, but D-14 leaves a written-off entry at `status = Active` with `collection_status = Written Off`. Read literally, a written-off balance would keep inflating the 90+ card, which would make the aging report overstate what the shop can actually collect — the exact opposite of AR-01's purpose.

Binding contract:

- The six **bracket cards and the six bracket tabs contain only open entries** — `collection_status` not in (`paid`, `written_off`).
- A separate **"Closed" tab** lists the `paid` and `written_off` entries, with the same columns, so nothing disappears from Accounting's view.
- The **"All" tab shows open entries only**, consistent with the cards. "Closed" is the deliberate opt-in.

The planner must carry this into the controller query, not just the client-side filter, so the card totals are computed server-side over the same open set.

**Deliberately absent from this surface** (each present in the demo, each rejected):

- **"Export"** — Phase 8 RPT-05 solves export once for every report. A button that does nothing is worse than no button.
- **Date-range filter** — an as-of-date aging view is a reporting feature (Phase 8 RPT-01/RPT-04), not a working list.
- **Search by client / JO number** — the working set is dozens of rows across eight tabs. Search is a reasonable Phase 8 addition once the closed set has years of history in it; it is not needed to satisfy AR-01 and is not built here.
- **"Entry Type" column and filter** — the demo's `Partial Payment` / `Cancellation Fee — Unpaid` distinction is the AR model D-01 explicitly rejects. There is exactly one kind of AR entry in this system: an Owner-approved On-Credit balance. No column, no filter.
- **Payment adjustment modal** — CONTEXT.md `<deferred>` rules it out by name.

### 2. AR entry detail (`resources/js/pages/accounting-staff/AccountsReceivable/Show.vue`, new)

Breadcrumbs: "Accounts Receivable" → "{JO number}". H1 "{JO number}" (Display) with "{customer} · {description}" beneath (Body, muted), then the aging bracket and collection status badges side by side at `sm` (8px) gap.

Panels, stacked at `lg` (24px) gaps, each a `Card` with a Heading:

1. **Pending write-off `Alert`** (only when a request is open) — lucide `Clock`, default `Alert` variant (**never `variant="destructive"`** — a pending request is a waiting state, not an error), copy per the Copywriting Contract. Modelled on the demo's "Pending Owner/Admin approval" banner, narrowed to Owner-only per `AccountsReceivablePolicy`'s existing deliberate split.
2. **Amounts** — four rows: "Credit Extended" (the stored `accounts_receivable.balance`, i.e. what was approved), "Job Order Total", "Amount Paid", "Outstanding Balance". The first three at Body; Outstanding at Display. The footnote line explains the derivation so nobody hunts for an edit control. **This is the only surface that shows "Credit Extended"** — the aging list omits it, per CONTEXT.md `<specifics>`'s "the three-column display is fine, the three stored fields are not".
3. **Account Details** — a two-column `grid` of caption/value pairs at Label/Body: Approved On, Due Date, Days Past Due, Aging Bracket, Last Reminder Sent.
4. **Collection Status** — a `Select` (`w-56`) limited to the four human-settable values, plus an "Update Status" `--primary` submit at `sm` (8px) gap, inside an Inertia `<Form>` bound to the Wayfinder action. Helper text beneath. For a terminal (`paid` / `written_off`) entry the control is **not rendered at all** — only the badge and the muted explanation line. A disabled `Select` would leave the user hunting for what to enable.
5. **Actions row** — "Print Collection Letter" (`variant="outline"`, lucide `Printer`) and "Request Write-Off" (`variant="outline"`, lucide `FileMinus`), at `sm` (8px) gap. The letter button is absent for a `Current` entry, replaced by the muted line from the Copywriting Contract. The write-off button is absent when a request is already pending (the banner in ⑴ is the state) and when the entry is terminal.
6. **Activity** — a read-only, newest-first list of the entry's `audit_trail` rows: action description, actor name, timestamp. Capped at the most recent 20 with no pagination and no filters. This is CONTEXT.md's optional item, built because a collections workflow is judged on what was already tried — "Follow-up call placed, May 22" is the whole reason the next call is different. **It reads `audit_trail`; it never writes a parallel log.** If the planner finds the audit payload shape too costly to render inside this phase's budget, the correct move is to **drop the panel entirely**, not to add a log column or table.

### 3. Collection letter (`resources/js/pages/accounting-staff/CollectionLetter.vue`, new)

Same shape as `cashier/Receipt.vue`: a read-only Inertia page, a `print:hidden` "Print Letter" button above the document, and `window.print()`. `AppSidebar.vue` and `AppSidebarHeader.vue` already carry `print:hidden` (verified), so **no new print CSS is required** — the printed page is the letter alone.

- The letter `Card` is `class="mx-auto w-full max-w-2xl print:border-0 print:shadow-none"`. Dropping the border and shadow in print is the one refinement over `Receipt.vue`: a receipt reads fine as a bordered slip, a formal letter must not print inside a visible box.
- Document order: letterhead (Display) → `border-t` rule → date line → addressee → reference line → the bracket-driven body paragraph → the three-row amount block with "Amount Due" at Display → due date / days-past-due line → payment instruction → "Sincerely," → signature rule and block → muted print footer. `xl` (32px) gaps between letterhead, body, and signature block; `md` (16px) between paragraphs.
- **The letter quotes the current derived outstanding balance as "Amount Due"** — this settles `07-RESEARCH.md` Open Question 2. A letter demanding money the customer already partly paid destroys its own credibility and invites a dispute. "Credit Extended" and "Amount Paid" appear above it so the three numbers reconcile on the page and the customer can check the arithmetic.
- Body copy is selected by the entry's aging bracket at render time and **never persisted** (D-12). Four bodies over five overdue brackets: 61–90 and 90+ share the final notice, exactly as D-12 specifies.
- **No editable field of any kind.** CONTEXT.md rejected a pre-print textarea by name; the print button is the only control on the page.

### 4. Owner write-off queue (`resources/js/pages/owner/WriteOffRequests.vue`, new)

Differences from `CreditRequests.vue`:

**What a rejected request looks like afterward:** nothing. The `write_off_*` columns are nulled, the entry returns to unflagged Active, and the rejection lives in the activity log (§2 ⑹). **Do not add a "Write-Off Rejected" badge** — no column backs it, and inventing one would recreate the flat multi-value status list D-09 rejected.
