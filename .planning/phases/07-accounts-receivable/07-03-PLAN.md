<objective>
Build the daily reminder command AR-02 describes literally: as each Active AR entry crosses into a reminder-bearing aging bracket, Accounting Staff and Owner both receive an escalating email (D-06) -- never the customer -- with the send wrapped in Phase 4's mail-failure isolation (D-05) so a transport outage can never break the bracket transition.

Purpose: This is the automation half of Phase 7 -- no UI surface, but it is the one AR-02 success criterion the phase cannot claim without a working, tested, idempotent scheduled job.
Output: `SendAccountsReceivableReminders` command (the project's first), `AccountsReceivableReminder` Mailable + Markdown view, and the `routes/console.php` schedule registration.

**Idempotency design decision (RESOLVED per D-17 -- user's binding answer to RESEARCH.md Open Question 1, recorded 2026-09-08):** "Fire once per bracket, then stop." This plan uses D-07's literal single-fire-per-bracket mechanism -- one `last_reminder_bracket` column, compared by `rank()`, no daily re-email at the terminal 90+ bracket. D-08's "never go quiet after the 90+ final notice" is satisfied because a 90+ entry never leaves the aging list, the six bracket cards, or (once requested) the Owner's write-off queue until it closes -- visibility, not a recurring email, is what "never goes quiet" means here. This keeps the schema to the single column 07-01 already added and avoids a second, untested recurring-mail code path for a behavior CONTEXT.md never explicitly asked for in those terms.

**Auto-close design decision (resolves the D-10/D-16 "system-set Paid" mechanism):** D-16 deliberately keeps zero AR-side code on the Cashier's payment write path. This command is therefore the one place that lazily notices a settled balance: on every run, before computing a bracket, it checks the derived outstanding balance and stamps `collection_status = paid` the first time it sees zero or less, then skips that entry for the rest of the run. This is read-time housekeeping in AR-owned code, not a write-path hook -- consistent with D-16 and the only mechanism available to satisfy D-10's "Paid is system-set" without inventing a payment-side observer.
</objective>

    Create `app/Console/Commands/SendAccountsReceivableReminders.php`: `protected $signature = 'ar:send-reminders';`, `protected $description = 'Send escalating AR reminder emails as entries cross aging brackets (AR-02).';`. `public function handle(): int`: query `AccountsReceivable::query()->where('status', AccountsReceivableStatus::Active->value)->whereNotNull('due_at')->whereNotIn('collection_status', [AccountsReceivableCollectionStatus::Paid->value, AccountsReceivableCollectionStatus::WrittenOff->value])->with(['jobOrder.transactions:id,job_order_id,amount,status', 'jobOrder.queueEntry.customer:id,name'])->chunkById(50, fn ($receivables) => $receivables->each(fn (AccountsReceivable $r) => $this->processOne($r)));` then `return self::SUCCESS;`.

    `private function processOne(AccountsReceivable $receivable): void`: compute `$amountPaid = (float) $receivable->jobOrder->transactions->where('status', TransactionStatus::Completed->value)->sum('amount');` and `$balance = $receivable->jobOrder->total_amount !== null ? round((float) $receivable->jobOrder->total_amount - $amountPaid, 2) : 0.0;`. If `$balance <= 0`: `$receivable->forceFill(['collection_status' => AccountsReceivableCollectionStatus::Paid->value])->save();` and `return;` (the auto-close decision documented in this plan's objective). Otherwise compute `$bracket = $receivable->agingBracket();`; if `! in_array($bracket, AccountsReceivableAgingBracket::reminderBearing(), true)` return with no write (display-only band, e.g. SixtyOneToNinety). Compute `$lastBracket = $receivable->last_reminder_bracket;` and `$crossedNewBracket = $lastBracket === null || $bracket->rank() > $lastBracket->rank();` (the cast already turns the column into an enum instance, per 07-01). If `! $crossedNewBracket` return with no write. Otherwise: `try { Mail::to($this->reminderRecipients())->send(new AccountsReceivableReminder($receivable, $bracket)); } catch (\Throwable $e) { report($e); }` then, OUTSIDE the try/catch and unconditionally after it, `$receivable->forceFill(['last_reminder_bracket' => $bracket->value, 'last_reminder_sent_at' => now()])->save();` (Pitfall 2 -- the stamp always happens, a mail failure is isolated and never rolls it back; `last_reminder_sent_at` is informational only, read by Show.vue's "Last Reminder Sent" field, and plays no role in the idempotency comparison above, which stays purely `rank()`-based on `last_reminder_bracket`).
