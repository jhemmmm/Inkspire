<objective>
Close the credit lifecycle AR-04 asks for: Accounting Staff can ask an Owner to write off a balance they cannot collect, and only the Owner can approve or reject it (D-13). This is also the only aging-adjacent surface Owner gets in this phase (D-04) -- a write-off queue, not a second copy of Accounting's aging list.

Purpose: This is the last vertical slice in Phase 7 and the one that finally lets a 90+ entry leave the working list for good.
Output: `WriteOffRequestController` (Accounting), `WriteOffApprovalController` (Owner), the extended `AccountsReceivablePolicy`, and the Owner's `WriteOffRequests.vue` queue.

**Revision note (checker Blocker 2):** `collection_status` and `AccountsReceivableStatus` are orthogonal columns per D-09 -- `status === Active` is never a sufficient guard on its own. Concrete race the checker identified: Accounting requests a write-off; before the Owner acts, the customer pays in full and the next `ar:send-reminders` run (07-03) stamps `collection_status = paid`; the Owner then approves the still-pending write-off, overwriting a correctly-settled account into a reported loss that Phase 8's reporting would read as ground truth. Both `WriteOffRequestController::store()` and `WriteOffApprovalController::approve()` now independently guard against this -- the latter inside its existing `lockForUpdate()` re-read, since the payment can land in the exact window between the Owner opening the queue and clicking Approve.

**Revision note (checker Blocker 3, user decision):** the `PaymentStatus::WrittenOff` regression closure on `cashier/Dashboard.vue` and `frontline-staff/Dashboard.vue` (originally Task 3 of this plan) moved to `07-01-PLAN.md`, where the `WrittenOff` enum case is first introduced -- it is a completeness item for that change, and moving it keeps this plan under the file-count threshold.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05-01 | Elevation of Privilege | Non-Owner (Admin) attempts to approve/reject a write-off directly via URL | mitigate | `AccountsReceivablePolicy::approveWriteOff()`/`rejectWriteOff()` Owner-only check, enforced via each FormRequest's `authorize()` -- verified by an explicit Admin-gets-403 feature test, matching `CreditApprovalTest.php`'s existing precedent |
| T-07-05-02 | Tampering / Repudiation | Double-submit or replay of write-off approve/reject (network retry, double click, stale tab) | mitigate | Locked re-read (`lockForUpdate()` inside `DB::transaction()`) + `abort_if(write_off_requested_at === null)` re-check, identical to `CreditApprovalController`'s established CR-05 concurrency guard |
| T-07-05-03 | Tampering | Client attempts to set `job_orders.total_amount` or fabricate a transaction alongside a write-off approval | mitigate | The approval action only ever writes `collection_status` and `payment_status`; no request field controls `total_amount` or `transactions`, and D-14's "not altered" rule is verified by an explicit test asserting `total_amount` is unchanged after approval |
| T-07-05-04 | Repudiation | Write-off request/approval/rejection with no traceable actor or reason | mitigate | `write_off_requested_by`/`write_off_reason`/`write_off_requested_at` are always stamped from server-side `$request->user()->id`/`now()`, never client-supplied identity; `#[ObservedBy(AuditObserver::class)]` captures every write automatically |
| T-07-05-05 | Tampering (business-logic race) | A payment settles an entry (`collection_status = paid`) in the window between a write-off request and the Owner's approval, which would otherwise overwrite a correctly-paid account into a reported loss | mitigate | `WriteOffRequestController::store()` rejects a request against an already-`paid`/`written_off` entry up front; `WriteOffApprovalController::approve()` independently re-checks the same condition INSIDE its `lockForUpdate()` re-read, so a payment landing after the request but before the click is still caught (Blocker 2, checker-identified) |
