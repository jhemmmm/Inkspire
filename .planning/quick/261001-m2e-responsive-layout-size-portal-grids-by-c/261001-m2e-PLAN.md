# Quick Task 261001-m2e: Responsive layout — size portal grids by their container

Source: `let-s-create-a-plan-twinkly-breeze.md`, section "5. Responsive layout" (sections 1-4 are done). Full decision detail and the breakpoint-choice table live in the orchestrator's `CONTEXT.md` for this task; this plan reproduces everything an executor needs so it is self-contained.

Goal: page grids size themselves by the real content width `PageContainer` has (viewport minus the 288px/54px sidebar minus padding), not by the raw viewport. Today a 4-tile `StatCard` row clips money and wraps "15 / 15" at 1280-1366px because `xl:grid-cols-4` fires on viewport width alone. This task converts every in-scope viewport layout class to a Tailwind v4 container-query class (`@container` on the parent, `@lg:`/`@3xl:`/etc. on children) so the grid reacts to the box it actually has.

Locked decisions are numbered D1-D9 below; task tables cite them inline. Do not revisit a locked decision.

1. **D1 — `PageContainer.vue` becomes the query container.** Add the `@container` class to its root. Nothing else about it changes except one added sentence in its existing template comment explaining why.
2. **D2 — Only LAYOUT variants convert**, everywhere in the inventory (Tasks 1-3 below): `grid-cols-*`, `col-span-*`, `flex-row`/`flex-col`/`flex-wrap`, `items-*`/`justify-*` paired with a converted `flex-row`, fixed widths (`sm:w-56` etc.), `ml-auto`, and `hidden`/`block`/`grid` display toggles. Padding, margin, gap and text-size variants (e.g. `sm:p-6`, `sm:px-6`) stay on the viewport and are never touched.
3. **D3 — Container breakpoints chosen from minimum comfortable item width**, not a mechanical viewport→container rename. Container-query `rem` resolves against this app's 18px root, so Tailwind's container sizes are: `@sm` 432px, `@md` 504px, `@lg` 576px, `@xl` 648px, `@2xl` 756px, `@3xl` 864px, `@4xl` 1008px, `@5xl` 1152px. `PageContainer`'s content box is about 343px on a 375px phone, 454px at 820px with the sidebar, 640px at 1024px, 896px at 1280px, 982px at 1366px, 1152px at 1536px. The patterns applied in this task:

    | Pattern (by final column/state)                                                                                                                                                                  | Use                                                                                     |
    | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
    | 4 `StatCard` tiles (admin Dashboard x2, Expenses is 3 not 4 — see below)                                                                                                                         | `grid-cols-1 @lg:grid-cols-2 @5xl:grid-cols-4`                                          |
    | 3 `StatCard`-shaped tiles (Expenses totals, artist Dashboard, PerformanceReport, and the `dt`/`dd` triplet-row in JobOrderWorkspace treated the same way since each item needs comparable width) | `grid-cols-1 @lg:grid-cols-2 @3xl:grid-cols-3`                                          |
    | 6 small figure tiles, base already 2 (AR aging brackets)                                                                                                                                         | `grid-cols-2 @2xl:grid-cols-3 @5xl:grid-cols-6`                                         |

4. **D4 — `TableFilterBar.vue`'s `sm:` layout variants become `@lg:`** too, so every page using it follows the same container (it already sits inside `PageContainer`).
5. **D5 — `StatCard.vue`:** add `whitespace-nowrap` to the value element only. Nothing else about `StatCard` changes.
6. **D6 — Empty state inside a wide table on a phone.** `TableEmpty` centres content across the table's full scroll width, pushing it off-screen on a phone. Fix: `DataTableCard.vue`'s root gets `@container` (unnamed); `EmptyState.vue`'s root gets `sticky left-0 w-[calc(100cqw-2rem)] max-w-full`. Confirmed: `TableCell.vue` is `px-4` and `TableEmpty.vue`'s own cell override is `p-4` — tailwind-merge resolves the conflict to `p-4`, so the true horizontal padding is `1rem` each side = `2rem` total, matching the `2rem` in the calc. Outside a table, `max-w-full` caps `EmptyState` at its parent so bare-panel usages (every portal dashboard's search-empty state, `QueueList.vue`, `frontline-staff/Dashboard.vue`, `accounting-staff/Dashboard.vue`) are unchanged — confirmed all of those already render inside `PageContainer`, so `100cqw` always has a container to resolve against. Confirmed by re-reading every inventory file: no converted `@…:` layout class in Tasks 1-3 sits inside a `DataTableCard` expecting `PageContainer`'s width — the only classes nested inside a `DataTableCard` are `EmptyState`'s own (handled by this decision).

8. **D8 — `container-type: inline-size` makes `PageContainer` a containing block for `position: fixed` descendants.** Re-grepped: the only matches for the literal word "fixed" inside in-scope files are prose (`BarChart.vue` "a fixed readout", `JobOrderPriceFields.vue` "not fixed values", `PageContainer.vue`'s own comment) — zero actual `class="...fixed..."` usages exist inside any `PageContainer`-wrapped page. **Reasoning for the two non-mechanical choices in this task:**

- **NewVisit.vue line ~574 (`sm:block`).** `SidebarProvider.vue` flips to mobile/overlay mode at `(max-width: 768px)` (`useMediaQuery("(max-width: 768px)")`), so at the original `sm:` breakpoint (640px viewport) the sidebar is never persistent — content width there is viewport minus `PageContainer`'s padding only (`p-4`→`sm:p-6`, i.e. 24px/side right at 640px), ≈592px. The closest container breakpoint to 592px is `@lg` (576px), not `@xl` (648px) — hence `@lg:block`.
